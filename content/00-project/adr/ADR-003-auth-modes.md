# ADR-003: Режимы авторизации и профили эндпоинтов

**Дата:** 2026-08-13

**Частично замещено [ADR-025](ADR-025-single-auth-mode.md)** (2026-09-08): режим персонального
ключа снят целиком — диспетчеризация по `AuthMode`, api-key-ветки диагностики и `SCOPE_LABELS`
этого решения отменены. Таблица профиля эндпоинтов (операция → путь) и разводка диагнозов 401/403
остаются в силе, упрощённые до одного режима — см. «Связанные статьи».

## Контекст

Клиент сегодня авторизуется единственным способом — query-параметром `sessionToken`, который
протухает без предсказуемого срока: 403 неотличим от прочих сбоев. Официальный интеграторский API
открывает персональный ключ через заголовок `X-Auth-Token` и операции, которых у клиента сегодня
нет (скачивание файла, полный состав участников, архив, чат, диагностика ключа) — требование
[«Персональный API-ключ и расширение возможностей»](../../30-requirements/personal-api-key.md).

Эмпирический зонд боевого домена (session-режим и api-key-режим) даёт три факта, определяющих
архитектуру:

1. **Профиль эндпоинтов жёстко привязан к режиму.** Интеграторская поверхность (`/api/Domain/*`,
   `/api/Recordings/*`, `/api/ConferenceReports/*`) отвечает 401/403 по session-токену; внутренний
   контур (`/api/recordings`, `/api/conferencesHistory`) не входит в спеку вовсе. Буквальный
   перевод путей «на спеку» ломает session-режим — нужна таблица «операция → путь по режиму»
   (зафиксирована требованием, FR-6).
2. **401 и 403 — устойчиво разные диагнозы.** 401 = ключ/токен невалиден или истёк, 403 = ключ
   валиден, но не хватает scope (`application.recording.read` / `.reporting.read` /
   `.applications.read` — карта берётся из `description` операций спеки). Тело 403 в большинстве
   случаев пустое — опираться нужно на код ответа, не на тело.
3. **`access-info` (кандидат FR-11) сам требует scope, который диагностирует.** Ключ без
   `application.applications.read` не может прочитать собственный `scopes[]` через штатный путь —
   диагностика обязана деградировать, а не падать именно там, где нужнее всего.

Пагинация тоже расходится по режиму: внутренний контур отдаёт `{recordings:[]}` без токена
страницы (только `skip`-офсет), api-key-контур — `{entities:[], nextPageToken}` (курсор). `ktalk
sync` (FR-14) и архив (FR-9) обязаны обходить оба единым итератором, не полагаясь на поле, которого
в одной из форм ответа нет.

## Решение

**Селектор режима.** `Settings` вычисляет режим сам (не фабрика клиента): `KTALK_PERSONAL_API_KEY`
задан → api-key, иначе `KTALK_SESSION_TOKEN` задан → session, иначе — явная ошибка конфигурации
при старте. Оба заданы — побеждает ключ; предупреждение без значения секрета, `KTALK_SESSION_TOKEN`
дальше не читается вовсе. Режим — enum `AuthMode`, не строка и не булев флаг. `KTalkClient` получает уже
разрешённый режим и credential при конструировании и настраивает `httpx.AsyncClient` один раз
(заголовок либо query-параметр, не оба) — взаимная исключительность структурная, а не проверяемая
на каждый запрос.

**Профиль эндпоинтов — таблица, не подкласс на режим.** Рассмотрены два варианта. Наследование
(`SessionClient`/`ApiKeyClient` с общим интерфейсом) прозрачно на старте, но дублирует
retry/error-handling в двух местах и требует держать сигнатуры синхронно вручную — риск
расхождения при росте с 5 до 11+ операций. Выбрана декларативная таблица (`операция × режим → путь
+ scope + нормализатор`): одна точка диспетчеризации в клиенте читает таблицу; отсутствие записи
для режима — управляемый отказ («операция доступна только в режиме персонального ключа») до
сетевого вызова, не голый 401/403. Таблица дословно повторяет форму FR-6 — документация и код не
расходятся.

**Нормализация ответов и пагинация.** Оба контура приводятся к единой внутренней форме (элементы +
курсор конца страницы). Конец страницы определяется каждым нормализатором по-своему (session —
короткая/пустая страница `skip`-офсета, api-key — отсутствие `nextPageToken`), а не общим полем,
которого может не быть в конкретной форме ответа — это и есть дисциплина FR-9/FR-14. Единый
асинхронный итератор поверх этой формы использует и `ktalk sync`, и архив, без ветвления по режиму
в вызывающем коде.

**Диагностика (FR-5) и auth_status (FR-11).** Диагностика строится из кода ответа и требуемого
scope операции (из профиля), не из тела ответа — формат тела 401 нигде не подтверждён, тело 403 в
основном пустое. 401 → «обновите `KTALK_PERSONAL_API_KEY`» либо «обновите `KTALK_SESSION_TOKEN`» по
активному режиму; 403 в api-key-режиме называет конкретный недостающий scope из профиля операции;
403 в session-режиме (где понятия scope нет) — общее «доступ запрещён».

`auth_status`: api-key-режим сначала пробует `access-info`. 403 на самом этом запросе, по
определению из зонда (403 = ключ валиден), означает «ключ жив, но `applications.read` не выдан» —
статус деградирует (`alive=true`, `scopes=None`) без дополнительного запроса; 401 → ключ мёртв.
Session-режим (открытый вопрос BA закрыт здесь): эндпоинта-аналога нет структурно, не из-за
нехватки прав — `auth_status` делает пробный `list_recordings(top=1)` и возвращает только «токен
работает / не работает», с явной пометкой, что scope и срок действия для сессионных токенов не
существуют как понятие. Это честный предел режима, а не деградация.

**Маскирование ключа (NFR-5).** Секрет уходит из URL полностью в api-key-режиме (заголовок вместо
query) — самостоятельное улучшение против сегодняшнего `?sessionToken=`, который остаётся в
session-режиме без изменений (FR-3, вне рамок эпика). httpx маскирует в repr только
`Authorization`/`Proxy-Authorization` — `X-Auth-Token` под маскировку не попадает автоматически, а
`KTalkError` обязан строить текст из статичных контекстных строк, никогда — из
`str(request.url)`/`request.headers`. Дополнительный барьер — санитайзер по подстроке секрета на
границе CLI/MCP перед печатью любого необработанного исключения.

Детали — таблица профиля, псевдокод, форма DTO, карта scope→сообщение, сценарии деградации — в
[companion-спеке](../../40-architecture/ADR-003-auth-modes-spec.md).

## Последствия

**Позитивные:** один диспетчер вместо кода, размазанного по методам; отказ для недоступных
операций происходит до сети; диагностика не зависит от недокументированного формата тела ошибки;
единая пагинация закрывает FR-9 и FR-14 одним механизмом.

**Негативные:** таблица профиля — дополнительный уровень косвенности (путь операции не виден прямо
в теле метода, только в таблице); нормализаторы нужно писать для каждой формы ответа отдельно,
дублирования избежать не всегда получится (`participants[]` в session и `entities[].participants[]`
в api-key — разные схемы источника).

**Смягчение:** таблица профиля живёт рядом с константами путей в одном модуле, не размазана;
контракт нормализатора (вход/выход) — предмет unit-тестов на фикстурах для каждой пары (операция,
режим), не одного сквозного теста.

## Альтернативы

- **Подкласс на режим (`SessionClient`/`ApiKeyClient`).** Отклонено — дублирование
  error-handling, риск расхождения сигнатур при росте набора операций.
- **Держать один путь на операцию, конвертировать API под спеку целиком.** Отклонено эмпирически
  (зонд): ломает session-режим полностью, а не частично.
- **Строить диагностику по телу ответа, а не по коду.** Отклонено: тело 403 в основном пустое,
  формат 401 нигде не подтверждён спекой; код ответа — единственный стабильный сигнал.
- **`auth_status` всегда идти через `access-info`, без деградации.** Отклонено: `access-info`
  требует `application.applications.read`, которого у ключа на момент проектирования нет — упал бы
  ровно там, где диагностика нужнее всего.
