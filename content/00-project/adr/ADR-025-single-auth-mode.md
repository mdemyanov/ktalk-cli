# ADR-025: Единственный режим авторизации — снятие персонального API-ключа

**Дата:** 2026-09-08

## Контекст

[«Единственный режим авторизации»](../../30-requirements/single-auth-mode.md) (FR-42…FR-44,
issue #10, issue #11) отменяет часть ADR-003: два режима авторизации (сессионный токен,
персональный API-ключ) конкурировали молча — ключ побеждал без объяснения в тексте отказа, а
`auth-status` называл заведомо невалидный ключ «валидным» на 403 `access-info`. Оба факта
воспроизведены боевой сессией 07.09.2026. Снятие режима — не только смена приоритета:
`KTALK_PERSONAL_API_KEY` упоминается 126 раз в 45 файлах (`src/`, `tests/`, `README.md`) — это
публичная переменная окружения, а не внутренняя деталь; часть операций (`list-archive`) не имеет
рабочего пути ни в одном из оставшихся режимов.

## Решение

**1. Снятие двухуровневой диспетчеризации.** `AuthMode` (enum) удаляется — единственный
дискриминатор без второго значения вводит в заблуждение больше, чем помогает: он приглашает
следующего автора завести `if mode is ...` там, где ветвиться больше не о чем. `OPERATION_PROFILES`
схлопывается из `операция → режим → профиль|None` в `операция → профиль|None` (плоская форма — так
её уже описывает `openspec/specs/talk-api-auth-modes/spec.md`, требование «Endpoint profile is
keyed by operation»). `AuthContext` остаётся (маскирующий `__repr__` секрета — ценность независимо
от числа режимов), но теряет поле `mode`: `AuthContext(credential: str)`. `classify_response`
теряет параметры `mode`/`required_scope` — 401/403 разводятся так же, как сегодня для
session-ветки; `SCOPE_LABELS` и api-key-ветки обоих кодов удаляются целиком (scope — понятие
режима ключа, у сессии его нет и не будет). Все точки, ветвящиеся сегодня по `AuthMode.API_KEY`
(диспетчер клиента, пагинация `ktalk sync`, скачивание файла, чат, полный состав участников),
теряют свою api-key-ветвь и остаются с единственной, session-формой без условия — не «условие,
которое всегда true», а буквальное отсутствие условия. Детали по файлам — companion-спека.

**2. Однократное предупреждение (FR-43) — вне разрешения credential.** Обнаружение
`KTALK_PERSONAL_API_KEY` в окружении печатается один раз за вызов процесса, в точке входа
`cli.py::main()`, до диспетчеризации команды — не в `Settings`/`AuthContext.resolve`, которые эту
переменную больше не читают вовсе (FR-42 сильнее «прочитать и проигнорировать»: поле удаляется из
модели `Settings`). Текст статичен и не интерполирует значение переменной — не полагается только
на постфактум-маскирование; тем не менее проходит через `redact_secrets` тем же вызовом, что и
остальной вывод CLI — тот же барьер, а не второй. `redact_secrets` расширяется: помимо
`Settings().ktalk_session_token`, маскирует и `os.environ.get("KTALK_PERSONAL_API_KEY")`,
прочитанный отдельно от `Settings` (единственное место кода, которое всё ещё смотрит на эту
переменную — ради маскирования, не ради credential).

**3. `auth-status` — новая форма JSON и двухканальный сигнал (FR-44).** Поля `scopes` и
`expired_at` удаляются из `AuthStatus` и из `--json`-ответа целиком, не остаются `null` навсегда:
постоянный `null` читается как «может быть заполнено при других условиях», что для сессионного
токена неверно структурно (`auth.py:96–101` уже фиксирует: scope и срок действия — не про сессию).
Ответ: `{"alive": bool, "note": str | None}`. Код возврата `cmd_auth_status`
(`src/ktalk_cli/cli_sync.py`) перестаёт быть безусловным `0` — пробрасывается из `status.alive`:
`0` при `True`, `1` при `False`. Непарсящееся тело пробного запроса (`_auth_status_session`,
`src/ktalk_cli/client.py`) перехватывается отдельно от `KTalkAuthError` (`except ValueError` вокруг
`response.json()`) и возвращает `alive=False` с честной пометкой «ответ не удалось разобрать»,
а не даёт `json.JSONDecodeError` подняться как сырой текст ошибки.

**4. `list-archive` остаётся с громким предполётным отказом, не снимается.** Профиль
`OPERATION_PROFILES["list_archive"]` — постоянный `None`; вызов диспетчера подтверждённо (архив
никогда не имел пути под сессией — ADR-003, зонд) отказывает до сети, называя операцию
недоступной. Это не тот тихий отказ, из-за которого открыта волна: (а) срабатывает
детерминированно на КАЖДЫЙ вызов, не имитирует успех; (б) называет операцию и причину текстом, не
голым 401/403; (в) тот же путь (`_profile_for`), что уже нёс `get_room`/`create_meeting` в
api-key-режиме — не новый механизм, проверенный прецедент; (г) surfaced-исключение — `KTalkError`,
ловится общим `except Exception` в `cli.py::main`, печатается на stderr, код возврата — `1`, не
`0`. `get_participants_report` (нет CLI-команды, нет вызывающего кода) удаляется вместе с методом
клиента и записью таблицы — мёртвый код, не поверхность пользователя. `get_participants_full` не
теряет путь: `KTalkClient.get_full_participants` уже сегодня выбирает механизм по режиму на уровне
оркестрации, а не через таблицу профиля — session-ветка (дообогащение `get_recording` +
`get_conference`) остаётся единственной и безусловной; запись в таблице и функция
`full_participants_apikey` удаляются как мёртвый код api-key-ветки.

**5. Breaking change.** Версия — **3.0.0** (semver, снятие публичной переменной окружения и смена
формы `--json`-ответа `auth-status`). Публикация в PyPI в эту волну не входит (санкция владельца) —
версия фиксируется в `pyproject.toml` реализацией, релизный коммит по ритуалу `a1ffa7d` (2.0.0)
делается отдельно, когда публикация санкционирована. Файла `CHANGELOG` в дереве нет и не заводится
— ломающее изменение называется этим разделом и телом релизного коммита, тем же способом, что
2.0.0. Цена для пользователя, ранее державшего постоянный ключ: ручное обновление сессионного
токена по мере протухания — это НЕ восстанавливается автоматически снятием ключа, README обязан
называть эту цену явно (NFR-18).

**6. Каскад пяти capability-спек — отложен, не забыт.** `recording-data-access` («Archive listing
is api-key-only…») и `room-diagnostics` («Api-key mode fails closed…») содержат нормативные
`### Requirement:`, прямо противоречащие этому решению после его реализации — не описательное
упоминание переменной, а активное условие ветвления, которого больше нет.
`registry-sync-window`/`host-project-config-discovery`/`centralized-machine-storage` упоминают
переменную описательно (имя, а не условие) — ниже срочности. Правка всех пяти — отдельная задача
SA после этой волны, не часть неё (сфера принадлежит паре «требование → capability», ADR-021, не
единолично SA); откладывается явно, не умалчивается.

## Последствия

**Позитивные:** конкуренции режимов больше нет структурно — не по дисциплине, а по отсутствию
второго значения для сравнения; диагностика `auth-status` не может соврать про режим, которого
нет; профиль эндпоинтов — одна таблица без второго измерения, меньше мест для рассинхронизации.

**Негативные:** `list-archive` — постоянно нерабочая команда в `--help`, пока не удалена отдельным
решением; пять capability-спек временно противоречат факту снятия режима до отдельной правки;
пользователи с постоянным ключом теряют beспрерывность работы без ручного обновления токена.

**Смягчения:** `list-archive`-отказ — текстово честный и детерминированный (см. п.4), не путается с
сетевым сбоем. Противоречие спек названо явно (п.6), не откладывается молча. README (NFR-18)
называет цену ручного обновления токена до того, как пользователь на неё наткнётся.

## Альтернативы

- **Снять `list-archive` вместе с режимом (убрать подкоманду).** Отклонено: это отдельное
  breaking-изменение CLI-поверхности (argparse "invalid choice" вместо явного текста), не входит в
  предмет отмены режима авторизации; громкий предполётный отказ дешевле и информативнее для
  пользователя, чем исчезновение команды.
- **Оставить `scopes`/`expired_at` как постоянный `null`.** Отклонено: `null` навсегда неотличим от
  «пока не реализовано» — то же семейство нечестности, за которое открыта волна (issue #11).
- **Оставить `AuthMode` как задел на будущий третий режим.** Отклонено: YAGNI — ни требование, ни
  BA не называют кандидата на новый режим; дискриминатор без второго значения — источник мёртвого
  ветвления, не архитектурный запас.
