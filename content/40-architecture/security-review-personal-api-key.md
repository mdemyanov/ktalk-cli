# Security review: персональный API-ключ (SEC-001)

Режим персонального API-ключа, предмет этого ревью, снят [ADR-025](../00-project/adr/ADR-025-single-auth-mode.md).
Документ сохранён как исторический след ревью реализации снятого режима на момент её принятия —
не описывает текущую поверхность пакета. Ревью session-only поверхности, оставшейся единственной,
этой волной не заказано (решение владельца — роль DevSecOps не включена в волну ADR-025).

DevSecOps-ревью реализации эпика «персональный API-ключ» (0.5.0) перед merge. Скоуп:
`src/ktalk_mcp/` целиком, с фокусом на `client.py`, `auth.py`, `config.py`, `cli.py`,
`cli_sync.py`, `download.py`; входы — [требование](../30-requirements/personal-api-key.md)
(NFR-5), [ADR-003](../00-project/adr/ADR-003-auth-modes.md) (раздел про маскирование),
[client-modules-spec.md](client-modules-spec.md), [dev-notes](../60-implementation/personal-api-key-dev-notes.md).

На момент ревью: 152 теста зелёные, ruff чист (заявлено Dev). После правок этого ревью:
**157 тестов зелёные** (152 + 5 новых регрессионных), `ruff check src/ tests/` чист,
`scripts/check.sh --fast` — `Errors: 0`.

## Вердикт по NFR-5 (ключ не логируется/не попадает в трейсбэки/вывод CLI)

**Выполняется — с двумя найденными и закрытыми в рамках этого ревью пробелами.**

- Ни один из пяти путей построения текста ошибок (`KTalkClient._classify`,
  `OperationNotAvailableError`, `KTalkConfigError`, `download.py`, `auth.py`) не строит
  сообщение из `str(request.url)`/`request.headers`/`repr(request)`/`repr(response)` —
  проверено построчно, подтверждено существующими `test_secret_masking.py`.
- httpx не маскирует `X-Auth-Token` в `repr(Headers)` (только `Authorization`/
  `Proxy-Authorization`) — подтверждено экспериментально; это не создаёт риска только
  потому, что нигде в кодовой базе `repr(headers)`/`repr(client)` не печатается.
- Найдено (и исправлено): `Settings` (pydantic) по умолчанию печатала значения секретных
  полей в `repr()`/`str()` — не эксплуатировалось ни одним текущим call site, но было
  спроектированной архитектурой недосмотром: `AuthContext` уже явно маскирует себя
  (`config.py`/`auth.py`), `Settings` — нет. Закрыто (`Field(repr=False)`).
- Найдено (и исправлено): ADR-003 явно проектировал «SecretRedactor» — «санитайзер по
  подстроке секрета на границе CLI/MCP перед печатью любого необработанного исключения»
  — но он нигде не был реализован и не вызывался. Добавлен `config.redact_secrets()`,
  подключён в единственную существующую точку печати необработанных исключений в CLI
  (`cli.py::main`) и в оба `except`-блока `cli_sync.py`.
- Не закрыто в рамках этого ревью (см. «Вынесено на решение»): в session-режиме
  `sessionToken` — client-level default query-параметр `httpx.AsyncClient`, который
  httpx подставляет в **любой** запрос через этот клиент, включая абсолютные URL на
  чужой хост. `download.py` в session-режиме использует `fileUrl` из ответа API «как
  есть» — если это когда-либо окажется абсолютным URL на другой домен (а не
  подтверждённый зондом относительный путь), `sessionToken` уйдёт третьей стороне.
- pydantic `ValidationError` не эксплуатируется: оба секретных поля — `str | None` без
  валидаторов, `Settings()` физически не может упасть с `ValidationError` на них
  сегодня — проверено (см. чек-лист «Проверено и чисто»).

## Вердикт по политике записи файла в `download.py`

**Базовый минимум SA/Dev достаточен как guard от случайной перезаписи, но НЕ является
защитой от произвольной записи в файловую систему — это осознанный, непринятый риск,
требующий решения PM/SA до расширения доверия к вызывающей стороне MCP-инструмента.**

Что уже защищено (проверено, в т.ч. новым тестом):
- Перезапись существующего файла без `overwrite=True` — отказ (`FileExistsError`).
- TOCTOU-гонка между проверкой и записью и запись «сквозь» оборванный symlink —
  закрыто в рамках этого ревью (`os.O_EXCL`, см. находку SEC-001-06).

Что НЕ защищено и осталось так по замыслу SA («сознательно не проектировал политику,
полное ревью — DevSecOps»):
- `target_path` принимается от вызывающего без каких-либо ограничений: абсолютный путь,
  `..`-компоненты, путь вне какой-либо «ожидаемой» директории — всё разрешено. Инструмент
  `ktalk_download_recording` физически эквивалентен «записать произвольный файл куда
  скажут» с правами процесса MCP-сервера.
- Если `overwrite=True` передан вызывающим — существующий symlink (не оборванный) будет
  прозрачно разыменован, и запись уйдёт по цели symlink'а. Это уже осознанно запрошенное
  вызывающим поведение (semantics «перезаписать» включают «перезаписать то, на что
  указывает путь»), не регресс этого ревью.

Вердикт: **для однопользовательского локального MCP-сервера (текущая модель
использования — личный ассистент под управлением оператора) риск приемлем при условии,
что оператор доверяет своему MCP-клиенту** (тот же уровень доверия, что и любой другой
инструмент с побочными эффектами на файловой системе). Риск становится неприемлемым,
если сервер когда-либо будет запущен в модели с менее доверенным вызывающим (например,
многопользовательский/расшаренный процесс, или агент, чей `target_path` может быть
подсказан текстом из внешнего источника — заголовок записи, транскрипт, комментарий —
классический prompt injection вектор для MCP-инструментов с побочными эффектами). Если
эта модель использования на горизонте — нужна политика "safe root" (переменная вроде
`KTALK_DOWNLOAD_DIR`, отказ для путей, чей `resolve()` не является потомком корня). Это
архитектурное решение (новый env var, новый контракт параметра), не мой мандат — вынесено
ниже.

### SEC-001-01 (Medium) — `Settings.__repr__`/`__str__` печатали секреты в открытом виде

**Файл:** `src/ktalk_mcp/config.py`, поля `ktalk_session_token`/`ktalk_personal_api_key`
(было — строки 46-47 до правки).

**Воспроизведение (до фикса):**
```python
from ktalk_mcp.config import Settings
s = Settings(ktalk_personal_api_key="pk-...")
repr(s)  # -> "Settings(..., ktalk_personal_api_key='pk-...', ...)"
```
pydantic `BaseModel`/`BaseSettings` по умолчанию включает значения всех полей в
`__repr__`/`__str__`. `AuthContext` (`auth.py`) уже явно переопределяет `__repr__` ради
этого самого риска — `Settings` была пропущена. Сегодня в кодовой базе НИ ОДИН call site
не печатает `Settings()` целиком напрямую (проверено `grep`), поэтому эксплуатации не
было — но это landmine: любой будущий `print(settings)`/`logger.debug("cfg: %s", settings)`
в отладочных целях тривиально утёк бы секрет целиком.

**Фикс:** оба поля объявлены `Field(repr=False)` (pydantic 2.x) — значение полей по-прежнему
доступно программно (`.ktalk_personal_api_key`), но не попадает в `repr`/`str`.

**Тест:** `tests/test_secret_masking.py::test_secret_not_in_settings_repr_or_str`.

### SEC-001-02 (Medium) — спроектированный «SecretRedactor» не был реализован

**Файлы:** `src/ktalk_mcp/config.py` (новая функция `redact_secrets`), подключение —
`src/ktalk_mcp/cli.py:234-235`, `src/ktalk_mcp/cli_sync.py:84,131`.

ADR-003 (раздел «Маскирование ключа») текстом фиксирует: «Дополнительный барьер —
санитайзер по подстроке секрета на границе CLI/MCP перед печатью любого необработанного
исключения». В `content/40-architecture/ADR-003-auth-modes-spec.md` этот компонент даже
назван явно — `SecretRedactor` (таблица «Компоненты»). Ни в `src/ktalk_mcp/` (проверено
`grep -rn "Redactor\|redact\|sanitiz\|mask"`), ни в разделе «Расхождения со спекой» dev-notes
этот пробел не упомянут — тихо выпал между спекой и реализацией.

Практический риск сегодня низкий (все текущие пути ошибок строят текст из статичных строк
— см. чек-лист «Проверено и чисто»), но это единственный слой, спроектированный
специально на случай, если ЭТА гарантия когда-нибудь перестанет выполняться (например,
стороннюю зависимость обновят, и её исключение начнёт нести URL/заголовки). Без барьера
такой регресс дошёл бы до stderr пользователя необнаруженным ни одним из существующих
тестов NFR-5 (они проверяют текущие конкретные сценарии, не защиту "на будущее").

**Фикс:** `config.redact_secrets(text)` — вычитывает активные значения обоих секретных
env через `Settings()` и заменяет их в тексте на `***REDACTED***`; обёрнута в `try/except`,
чтобы сам барьер не мог стать новым источником отказа. Подключена в:
- `cli.py::main`, единственная точка печати любого непойманного исключения любой команды;
- `cli_sync.py::cmd_sync`/`cmd_auth_status`, оба `except _AUTH_ERRORS` блока.

**Тест:** `tests/test_secret_masking.py::test_secret_redacted_from_unexpected_exception_via_cli_main`
— монки-патчит обработчик команды `list` на исключение, не являющееся `KTalkError`
(симулирует «секрет случайно попал в текст стороннего исключения»), проверяет, что оно
всё равно доходит до `cli.py::main`'s `except Exception` и редактируется.

### SEC-001-03 / SEC-001-04 (High) — URL-инъекция через неквотированные path-параметры

**Файлы (было):**
- `src/ktalk_mcp/client.py::_call` — `path = profile.path_template.format(**path_params)`
- `src/ktalk_mcp/client.py::_fetch_chat_messages` — `f"/api/ConferenceReports/{conference_key}/messages"`
  и `f"/api/conferencesHistory/{conference_key}/chat/messages"`
- `src/ktalk_mcp/auth.py::full_participants_apikey` — `profile.path_template.format(key=recording_key)`

**Воспроизведение (подтверждено экспериментально, до фикса):**
```python
import httpx
c = httpx.Client(base_url="https://x.example", params={"sessionToken": "secret"})
req = c.build_request("GET", "/api/recordings/{key}".format(key="../admin"))
print(req.url)  # -> https://x.example/api/admin?sessionToken=secret
```
`recording_key`/`conference_key` — это ЛИБО значение, пришедшее от KTalk API (`id`/`key`
в ответах), ЛИБО параметр, переданный вызывающим MCP-инструмент напрямую
(`ktalk_get_recording(recording_key=...)`, `ktalk_get_chat_messages(conference_key=...)`
и т.д. — свободная строка, без валидации формата). Без квотирования `../`-сегменты в
значении меняют фактический путь запроса ДО того, как `OPERATION_PROFILES`-диспетчер
(центральная идея ADR-003 — «одна точка диспетчеризации, отказ для недоступных операций
до сети») успевает что-либо решить: путь уже не тот, что в профиле. Практический эффект —
вызывающий MCP-клиент может обратиться к произвольному GET-эндпоинту НА ТОМ ЖЕ ХОСТЕ
(база — `KTALK_BASE_URL`) с уже приложенным живым credential'ом (`sessionToken` в query
или `X-Auth-Token` в заголовке — оба остаются на месте, инъекция не меняет их), в обход
границы, которую профиль эндпоинтов должен был гарантировать. Секрет при этом НЕ
утекает — риск в обходе access-control-слоя, не в раскрытии credential'а.

`download.py::build_download_url` уже квотировал `recording_key`/`quality` корректно
(`urllib.parse.quote(..., safe="")`) — этот паттерн просто не был применён к остальным
трём местам, использующим `.format()`/f-строки для пути.

**Фикс:** новая функция `auth.quote_path_param(value) -> str` (тот же паттерн, что уже
использовал `download.py`), применена во всех трёх местах:
- `client.py:159` — `path_template.format(**{k: quote_path_param(v) for k, v in params.items()})`
- `client.py:268` — `key = quote_path_param(conference_key)` перед подстановкой в f-строку
- `auth.py:245` — `profile.path_template.format(key=quote_path_param(recording_key))`

**Тесты:**
- `tests/test_client.py::test_get_recording_quotes_path_traversal_in_key` — проверяет
  реальный байтовый путь запроса (`request.url.raw_path`) равен ожидаемому квотированному
  значению, а не схлопнутому `/api/admin`.
- `tests/test_client.py::test_get_chat_messages_quotes_conference_key` — тот же класс для
  `_fetch_chat_messages`.

Оба теста были воспроизведены как красные на до-фиксовой логике (проверено вручную
экспериментом с `httpx.Client.build_request`, см. воспроизведение выше) перед фиксом.

### SEC-001-05 (Medium) — session-токен может уйти на чужой хост через `download.py`

**Файл:** `src/ktalk_mcp/download.py`, ветка session-режима в `download_recording_file`
(`_resolve_session_quality`, использует `fileUrl` из ответа `get_recording()` как есть).

**Механизм (подтверждено экспериментально):**
```python
import httpx
c = httpx.Client(base_url="https://ktalk.example", params={"sessionToken": "SECRET"})
req = c.build_request("GET", "https://cdn.other-domain.example/file.mp4")
print(req.url)  # -> https://cdn.other-domain.example/file.mp4?sessionToken=SECRET
```
`httpx.AsyncClient`, сконфигурированный с `params={"sessionToken": ...}` при
конструировании (session-режим, `client.py::__init__`), подмешивает этот
default-параметр в **любой** запрос через этот клиент — включая абсолютный URL на другой
хост, не только относительные пути на `base_url`. Аналогично для api-key-режима: заголовок
`X-Auth-Token` тоже мерджится в любой абсолютный URL через тот же клиент (проверено тем же
экспериментом с `headers=`) — но `download.py` в api-key-режиме строит URL сам
(`build_download_url`, относительный путь), не подставляет чужой абсолютный URL, поэтому
для api-key-режима вектор не актуален.

Session-режим — актуален: `download_recording_file` в session-ветке использует
`match["fileUrl"]` из ответа `get_recording()` **без проверки, что это относительный путь
или путь на том же хосте, что `KTALK_BASE_URL`**. Текущая тестовая фикстура
(`tests/fixtures/recording-detail-with-qualities.json`) отдаёт относительный путь
(`/recording-blob/...`), и BA/зонд явно фиксирует: реальный поток скачивания в
session-режиме зондом не проверялся, только наличие поля (`personal-api-key.md`, FR-7 AC-1
— ручная проверка). Если КТалк когда-либо начнёт отдавать `fileUrl` в виде presigned-URL
на CDN/blob-хранилище (обычная практика для видео большого размера), `sessionToken`
автоматически, без единой строки нового кода, начнёт улетать на этот сторонний хост в
query-параметре — и, скорее всего, осядет в access-логах этого CDN.

**Почему не исправлено в рамках этого ревью:** решение требует архитектурного выбора —
как минимум одного из: (а) строить отдельный `httpx.AsyncClient` без default-credential'ов
специально для потокового скачивания по абсолютному URL, либо (б) валидировать
same-origin (`fileUrl` либо относительный, либо хост совпадает с `KTALK_BASE_URL`) и
отказывать/предупреждать иначе. Оба варианта меняют контракт `download.py`/`client.py` за
пределами локального патча — SA явно закладывал `client.py` как компонент с единственным
экземпляром `httpx.AsyncClient` на клиент («настраивает httpx.AsyncClient один раз при
конструировании») — решение должно приниматься на этом уровне, не патчем в `download.py`.

**Рекомендация (для SA):** ввести same-origin проверку `fileUrl` перед `client.stream(...)`
в session-ветке `download_recording_file`, либо документально зафиксировать, что
`fileUrl` ГАРАНТИРОВАННО относительный по контракту API (если это подтверждается зондом
на боевом домене) — тогда риск закрывается не кодом, а зафиксированным инвариантом с
явным AC. До этого решения — **эксплуатация не подтверждена (фикстуры/зонд показывают
только относительные пути), риск умозрительный, но не нулевой и не проверяемый тестами
сегодня.**

### SEC-001-06 (Medium) — TOCTOU и запись «сквозь» оборванный symlink в `download.py`

**Файл:** `src/ktalk_mcp/download.py::download_recording_file` (было —
`target.exists()` + `target.open("wb")`, раздельные вызовы).

**Воспроизведение (подтверждено экспериментально, до фикса):**
```python
import pathlib
target = pathlib.Path("/tmp/x/out.bin")
outside = pathlib.Path("/tmp/x/outside/evil.bin")  # ещё не существует
target.symlink_to(outside)
target.exists()  # -> False (симлинк "оборван" — .exists() следует за ссылкой)
with target.open("wb") as fh:
    fh.write(b"payload")
outside.exists()  # -> True — запись ушла туда, куда указывает symlink
```
`Path.exists()` следует за symlink'ами и возвращает `False` для «оборванной» ссылки
(указывающей на несуществующий путь) — оригинальная проверка `if target.exists() and not
overwrite: raise FileExistsError(...)` пропускает этот случай, и последующий
`target.open("wb")` пишет сквозь символическую ссылку в произвольное место, которое она
указывает. Это отдельно от TOCTOU-окна между самой проверкой и записью (между ними —
сетевой вызов `client.stream(...)`).

Эксплуатация требует, чтобы атакующий уже мог создать файл (symlink) по пути
`target_path` ДО вызова `ktalk_download_recording` — то есть уже имел какую-то запись в
той же директории (например, shared/world-writable временная директория с другим
владельцем процесса, либо тот же локальный пользователь, что и так уже управляет MCP-
клиентом — в этом случае привилегия не повышается). Severity Medium, не Critical: модель
угроз, в которой это эксплуатируемо, узкая, но исправление тривиально и без
компромиссов по поведению.

**Фикс:** атомарный `os.open(target, os.O_WRONLY | os.O_CREAT | (0 if overwrite else
os.O_EXCL), 0o644)` вместо раздельных `exists()`+`open()`. POSIX гарантирует: `O_CREAT |
O_EXCL` отказывает, если путь — уже существующий файл ИЛИ symlink (в том числе
оборванный), независимо от того, куда он указывает. Ранняя не-атомарная проверка
`target.exists()` до сетевого вызова сохранена как есть (быстрый отказ без траты сетевого
раунд-трипа для самого частого случая — обычный существующий файл), атомарная проверка
добавлена как настоящий барьер непосредственно перед записью. При `overwrite=True`
поведение не изменилось (перезапись, включая через существующий symlink, — уже осознанно
запрошена вызывающим).

**Тест:** `tests/test_download.py::test_download_refuses_to_follow_dangling_symlink_at_target_path`
— создаёт оборванный symlink, проверяет `FileExistsError` и что файл вне `tmp_path` НЕ
создан. Воспроизведено вручную на до-фиксовой логике (см. воспроизведение выше) — без
фикса запись бы прошла успешно.

### SEC-001-07 (Medium, вынесено на PM/SA) — политика записи `target_path` не ограничена

См. «Вердикт по политике записи файла в `download.py`» выше — SEC-001-06 закрывает
TOCTOU/symlink-класс, но не меняет того факта, что `ktalk_download_recording` пишет по
любому пути, который попросит вызывающий (абсолютный, `..`-относительный, куда угодно в
пределах прав процесса). Это осталось так по осознанному решению SA
(`client-modules-spec.md`, «Безопасность записи на диск — не входит в её рамки»),
подтверждённому Dev (`personal-api-key-dev-notes.md`, «базовый минимум, не полная
песочница»). Не мой мандат чинить самостоятельно — требует нового контракта параметра
(например, ограничение корневой директорией через новую переменную окружения) и,
возможно, изменения документированного поведения инструмента.

**Рекомендация PM/SA:** явно зафиксировать модель угроз для `ktalk_download_recording`
(доверенный локальный оператор vs. потенциально расшаренный/менее доверенный вызывающий)
и либо принять текущий риск письменно (ADR), либо спроектировать ограничение
(`KTALK_DOWNLOAD_DIR` + `resolve()`-проверка на предка).

### SEC-001-08 (Low, не исправлено) — `KTALK_BASE_URL` без валидации схемы/хоста

**Файл:** `src/ktalk_mcp/config.py`, поле `ktalk_base_url: str = "https://your-domain.ktalk.ru"`.

Значение принимается как произвольная строка без проверки схемы. Это НЕ классический SSRF
(значение приходит из статичной конфигурации оператора/деплоя, не из запроса на входе — MCP
tool call/CLI argument не может изменить его на лету), поэтому severity Low, а не Medium/High.
Тем не менее: если оператор по ошибке укажет `http://` вместо `https://` (например, при
локальной отладке против staging без TLS), и `sessionToken`/`X-Auth-Token` уйдут открытым
текстом по сети. Не исправлено намеренно — жёсткая валидация (например, обязательный
`https`) конфликтует с легитимными сценариями локальной разработки/тестового стенда без
TLS и требует продуктового решения (жёсткий отказ vs. предупреждение), не тривиального
патча.

**Рекомендация:** README уже документирует `KTALK_BASE_URL` как `https://...` — добавить
явное предупреждение о рисках `http://`; если появится потребность — валидатор,
выдающий warning (не hard-fail) при не-`https` схеме.

### SEC-001-09 (Info) — реальные credential'ы в ambient shell-окружении во время ревью

В процессе ревью обнаружено, что окружение, унаследованное инструментами этого ревью,
содержало реальные значения `KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`/`KTALK_BASE_URL`
(боевой домен) — тот самый «ambient env leak» после зонда PM, который dev-notes уже
упоминают как источник трёх сломанных тестов («Важный урок: любой новый секретный env var
... обязан быть явно занулён во ВСЕХ существующих тестах»). Значения НЕ попали ни в один
файл этого репозитория (проверено — см. SEC-001-10) и не воспроизводятся в этом отчёте.
Это не находка в коде, а операционная гигиена: реальные секреты в незакоммиченном
env — ожидаемо (это ровно то, для чего `.env`/env vars существуют), но сохраняющееся
присутствие боевого ключа в интерактивной оболочке разработчика — источник риска
случайной утечки при любом будущем `print`/сохранении сессии терминала/шаринге экрана.
**Рекомендация:** после завершения зонда/зачистки — `unset KTALK_SESSION_TOKEN
KTALK_PERSONAL_API_KEY` в шелл-профиле, хранить боевые значения только в `.env`
(gitignored, не экспортированный в интерактивный шелл) или secret-store.

  `OperationNotAvailableError`) не строится из `request.url`/`request.headers`/
  `repr(request)`/`repr(response)` — все сообщения статичные шаблонные строки с

- `AuthContext.__repr__` уже маскировал credential (`credential='***'`) — эталон, на
  который ориентировался и фикс `Settings`.
- `KTalkClient` не переопределяет `__repr__`, но и не нуждается — единственный
  нетривиальный атрибут (`_auth`) уже самомаскируется, `_client` — стандартный

- pydantic `ValidationError` не может обнажить секрет: оба поля — `str | None` без
