# Конфигурация проекта-хозяина плагина ktalk

Companion-спека (SA-003), детализирующая [FR-20, FR-21, FR-23, FR-24, NFR-11, NFR-16](../30-requirements/ktalk-plugin.md)
поверх границ, зафиксированных [ADR-012](../00-project/adr/ADR-012-plugin-boundary.md) (плагин —
тонкая обёртка, конфиг хозяина — дом «Проект-хозяин») и [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md)
(приоритет разрешения пути реестра). Значимого архитектурного решения сверх уже принятых в
ADR-012/ADR-013 здесь нет — формат файла и алгоритм discovery раскладывают уже согласованный
принцип «discovery принадлежит коду, не манифесту плагина» (RES-002, тема 3) по конкретной схеме.

## Контекст

11 файлов `.claude/` vault'а `naumen-cto` несут 27 вхождений `95_TRANSCRIPTS`, 4 вхождения
маршрутизации `20_MEETINGS/*`, ссылки на `10_PEOPLE`/`30_PROJECTS/active` — зашитыми в текст
промтов. Vault уже содержит `.claude/docs/vault-config.md` — таблицу «ключ → путь» с паттернами
имён файлов (RES-001 находка 4), но ни один актив её не читает программно: она существует как
текст для человека, не как контракт для кода.

RES-002 (тема 3) установила: конфигурация хозяина не приезжает плагину подстановкой манифеста —
`${CLAUDE_PLUGIN_ROOT}`/`${CLAUDE_PLUGIN_DATA}`/`${CLAUDE_PROJECT_DIR}` резолвятся только в
`.mcp.json`/`hooks.json`/`settings.json` плагина, не в теле промтов skills/agents. Discovery,
значит, обязан быть кодом пакета, а не декларацией плагина, и промты skills/agents не могут
получить путь через `{{подстановку}}` — им нужен другой канал.

**[ADR-012 §2а](../00-project/adr/ADR-012-plugin-boundary.md#2а-приоритетный-интерфейс-контура--cli-не-mcp)
(решение владельца, дополнено после первой редакции ADR-012):** в плагине приоритетна работа через
CLI `ktalk`, не через MCP-сервер. Это прямое следствие для этой спеки: канал, которым ключи
маршрутизации доходят до промтов skill/agent, — CLI (`ktalk <подкоманда> --json` через Bash), не
имя MCP-инструмента; discovery конфигурации хозяина живёт на одном пути исполнения (код пакета от
cwd) — MCP-транспорт из этой цепочки исключён, а не продублирован параллельной реализацией;
предусловие «`ktalk` в PATH» — жёсткое, без него не работает ни один сценарий навыка. MCP-сервер
остаётся вторичным путём для чтения контента (транскрипты, саммари) — его отказ не обязан
ломать реестровые/маршрутизационные сценарии (см. «Контракт деградации»).

## Формат файла конфигурации

| Параметр | Значение |
|---|---|
| Имя файла | `.ktalk.toml` |
| Расположение | корень проекта-хозяина (см. «Discovery» ниже) |
| Формат | TOML, парсится `tomllib` (stdlib Python 3.12, read-only) — без новой зависимости, соответствует конвенции стека (CLAUDE.md: «stdlib sqlite3 + argparse») |
| Владелец | код пакета `ktalk-mcp` (модуль `host_config.py`, отдельный от `registry.py` — грандфазер заморожен на 562 строках) |

**Конвенция «отдельный файл под своего владельца».** `.nauta-gates.yaml` принадлежит скриптам
`nauta`, `content/.doc-root.yaml` — плагину Gramax; `.ktalk.toml` по тому же принципу — не
пункт в `.claude/settings.json` и не переиспользование `vault-config.md` (markdown не
машиночитаем без парсера произвольной таблицы, TOML — machinery уже в stdlib). `vault-config.md`
остаётся человекочитаемым описанием для тех, кто не читает `.ktalk.toml` напрямую — не
дублирование source of truth, а два представления одного факта на переходный период (см.
«Миграция vault'а» ниже); после cutover `.ktalk.toml` — единственный вход для кода.

### Схема

```toml
[registry]
# Абсолютный или относительный (от каталога, где найден этот файл, см.
# «Discovery» ниже) путь к SQLite-реестру — точное правило резолюции в
# ADR-013-central-transcript-store-spec.md, «Поток данных» п.2.
# Отсутствует по умолчанию — при отсутствии ключа участвует следующий источник
# приоритета (ADR-013 §3): KTALK_REGISTRY_DB > машинный дефолт.
db_path = "95_TRANSCRIPTS/.registry.db"

[directories]
# Каталоги хозяина, используемые шагами обработки встречи для сопоставления
# участника/проекта. Отсутствующий ключ = каталог не объявлен (FR-24 деградация),
# не подставляется дефолтное имя каталога.
people = "10_PEOPLE"
projects_active = "30_PROJECTS/active"

[routing]
# meeting_type -> шаблон пути артефакта. Плейсхолдеры: {date} (YYYY-MM-DD), {id},
# {YYYY}, {type}, {title} — подставляются кодом/промтом, не этим файлом.
# Отсутствующий ключ = маршрут не объявлен (FR-21 деградация), не молчаливый
# фолбэк на путь другого ключа.
committee = "20_MEETINGS/committees/{id}/{date}.md"
standup = "20_MEETINGS/standups/{date}.md"
transcript_archive = "95_TRANSCRIPTS/{YYYY}/{date}_{type}_{title}.md"
eval_report = "95_TRANSCRIPTS/eval/reports/{date}_{title}.md"

[integrations]
# Заявленная доступность интеграций хозяина, не обнаруживаемых по пути.
# Отсутствие ключа трактуется как false (не заявлено) — не как "неизвестно,
# попробовать". FR-24: код всё равно обязан проверить фактическую доступность
# на старте шага, это поле — декларация намерения хозяина, не гарантия.
qmd = true
```

Все секции опциональны; пустой/отсутствующий файл эквивалентен «конфигурации нет» (FR-20 AC2).
Ни одно значение не имеет глобального «умного» дефолта, вычисляемого из других ключей — каждый
ключ либо объявлен явно, либо отсутствует (§ «Контракт деградации»).

### Поведение при малформенном файле

Симметрично `.nauta-gates.yaml` (CLAUDE.md, «Гейты»): файла нет → тихо, машинный дефолт (FR-20
AC2); файл есть, но не парсится TOML-синтаксисом ИЛИ проваливает валидацию схемы (неизвестный
top-level ключ вне `registry`/`directories`/`routing`/`integrations`; значение не строка там, где
ожидается строка; `integrations.qmd` не bool) → `HostConfigError`, называющая конкретный файл и
причину, процесс завершается на этом шаге, не продолжает работу на дефолте молча (FR-20 AC3).
Отличие от `.nauta-gates.yaml`: там ошибка — гейт коммита (CI), здесь — ошибка старта команды
CLI/MCP-сервера, тот же принцип «явная причина, не тихий откат», разное место применения.

## Discovery

1. Если задан `${CLAUDE_PROJECT_DIR}` (Claude Code выставляет его для plugin-контекста, RES-002
   тема 3) — конфиг ищется ровно по пути `${CLAUDE_PROJECT_DIR}/.ktalk.toml`. Обхода вверх нет:
   переменная уже называет корень проекта авторитетно, обход поверх неё внёс бы двусмысленность,
   которую платформа уже сняла.
2. Если `${CLAUDE_PROJECT_DIR}` не задан (голый CLI-запуск `ktalk` вне контекста Claude Code,
   например, из терминала) — обход вверх от `cwd`: на каждом уровне проверяется `.ktalk.toml`.
   Обход останавливается на первом найденном файле (он и есть результат) **или** на первом
   каталоге, содержащем `.git` (граница проекта — если конфига там нет, дальше не ищем: конфиг
   каталога-предка чужого репозитория не должен молча подхватываться), **или** на корне
   файловой системы — что наступит раньше.
3. Ничего не найдено в обоих случаях → FR-20 AC2: не ошибка, конфигурации нет, работа продолжается
   на источниках ниже по приоритету (env/дефолт).
4. Несколько кандидатов на разных уровнях обхода (шаг 2) не имеют смысла в этой схеме: обход
   останавливается на первом найденном — глубже не смотрит. Слияния конфигов разных уровней нет:
   частичный конфиг родителя, дополненный частичным конфигом потомка, дал бы неочевидную гибридную
   раскладку — конфликтует с «деградация обязана быть явной, не наполовину выполненной» (FR-24).
5. Стыковка с ADR-013 §3 (приоритет `--db > KTALK_REGISTRY_DB > конфиг хозяина > машинный дефолт`):
   `registry.db_path` из найденного конфига — третий источник. Discovery выполняется один раз на
   старте процесса; `resolve_db_path` принимает уже распарсенный `HostConfig | None` как параметр,
   не выполняет обход сам (разделение: discovery — до, резолюция приоритета — после, разные
   ответственности, разные модули — `host_config.py` и `config.py`).

## Маршрутизация как конфигурация

Сегодня в промтах `.claude/` зашиты 4 маршрута и 2 каталога-справочника. Перенос в `.ktalk.toml`
не меняет ни одного пути на живом vault'е (NFR-11) — конфиг объявляет то же самое, что промты
делают сегодня напрямую.

| Ключ | Пример пути (naumen-cto сегодня) | Плейсхолдеры |
|---|---|---|
| `routing.committee` | `20_MEETINGS/committees/{id}/{date}.md` | `{id}`, `{date}` |
| `routing.standup` | `20_MEETINGS/standups/{date}.md` | `{date}` |
| `routing.transcript_archive` | `95_TRANSCRIPTS/{YYYY}/{date}_{type}_{title}.md` | `{YYYY}`, `{date}`, `{type}`, `{title}` |
| `routing.eval_report` | `95_TRANSCRIPTS/eval/reports/{date}_{title}.md` | `{date}`, `{title}` |
| `directories.people` | `10_PEOPLE` | — (справочник, не шаблон) |
| `directories.projects_active` | `30_PROJECTS/active` | — (справочник, не шаблон) |

### Как ключи доходят до промтов навыка/агента

Подстановок в промтах нет (RES-002, тема 3) — промт не может сам прочитать `.ktalk.toml`. Канал —
существующая конвенция проекта: CLI с `--json` для машинного чтения (CLAUDE.md, «Conventions»).
Новая команда `ktalk config show --json` печатает распарсенный и провалидированный конфиг
(результат discovery + ADR-013 §3 резолюции `db_path`) целиком; промт skill/agent, дойдя до шага,
которому сегодня нужен зашитый путь, вызывает эту команду инструментом Bash **до** записи
артефакта и берёт из вывода нужный ключ (`routing.committee` и т.д.), сам подставляя уже известные
ему значения плейсхолдеров (`{date}`/`{id}` промт вычисляет сам — это не задача конфига). Код
пакета отвечает за discovery/валидацию/приоритет; промт — за подстановку плейсхолдеров в уже
полученный шаблон и за интерпретацию отсутствия ключа (см. «Контракт деградации»). Это то же
разделение ответственности, что RES-002 зафиксировала для `db_path` (FR-20/23): discovery — код,
не манифест; здесь оно же распространяется на маршрутизацию, не только на путь БД.

`ktalk config show` без `--json` печатает то же в человекочитаемой форме — по конвенции остальных
команд реестра. Команда входит в `_REGISTRY_FREE_COMMANDS` (`cli.py`) — конфиг хозяина не требует
открытия SQLite.

## Контракт деградации (FR-21, FR-24)

Деградация — явная и не частичная: шаг либо выполняется полностью на доступных данных, либо
явно помечает недоступную часть, никогда не молчит и не подставляет предположение.

| Условие | Поведение |
|---|---|
| Ключ `routing.*`/`directories.*` не объявлен (файла нет, или в нём нет этого ключа) | Шаг, которому нужен этот путь, не пишет файл и не угадывает путь — явно помечает результат как «маршрут `<ключ>` не объявлен в `.ktalk.toml`», продолжает остальные шаги, не зависящие от этого ключа (FR-21) |
| Ключ объявлен, но каталог физически отсутствует на диске | Отдельная от предыдущей пометка — «каталог `<путь>` объявлен, но не существует»: код/промт не создаёт каталог сам и не трактует это как «не объявлено» (два разных диагностических случая для одного и того же внешнего симптома «путь недоступен») |
| `integrations.qmd` отсутствует/`false`, ИЛИ объявлен `true`, но MCP-инструмент `qmd` фактически недоступен в сессии | Шаг сопоставления профиля помечает результат сопоставления как недоступный, не подставляет предположение об участнике (FR-24 AC1). Заявленное намерение (`integrations.qmd = true`) не заменяет фактическую проверку на старте шага — расхождение (заявлено, но недоступно) — тоже явная пометка, не тихий проброс |
| Доступна ровно одна из двух зависимостей (`qmd` или `directories.people`) | Шаг использует доступную, явно помечает недоступную — не останавливается целиком из-за одной отсутствующей (FR-24 AC2) |
| `KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`/интеграции чтения записей/транскриптов/саммари (не зависят от раскладки хозяина) | Работают независимо от наличия `.ktalk.toml` — не входят в контракт деградации этой спеки (FR-21 AC2, регрессия существующих MCP read-инструментов) |
| MCP-сервер недоступен/не стартовал (ADR-012 §2а: вторичный путь) | Реестровые и маршрутизационные сценарии навыка не зависят от MCP вовсе — они идут через CLI; отказ MCP ограничивает только вторичные MCP-инструменты чтения контента, не блокирует и не деградирует ни один из путей, описанных в этой спеке |

## Миграция vault'а на конфиг

Цель — объявить сегодняшнюю раскладку `naumen-cto`, ничего не передвигая (NFR-11). Прямой перенос
`vault-config.md` (RES-001 находка 4) в `.ktalk.toml`, один в один по значениям:

```toml
[registry]
db_path = "95_TRANSCRIPTS/.registry.db"

[directories]
people = "10_PEOPLE"
projects_active = "30_PROJECTS/active"

[routing]
committee = "20_MEETINGS/committees/{id}/{date}.md"
standup = "20_MEETINGS/standups/{date}.md"
transcript_archive = "95_TRANSCRIPTS/{YYYY}/{date}_{type}_{title}.md"
eval_report = "95_TRANSCRIPTS/eval/reports/{date}_{title}.md"

[integrations]
qmd = true
```

Ключи `vault-config.md` без прямого эквивалента в текущей схеме (`templates_dir`, `decisions_dir`,
`domain_dir`, `competitors_dir`, `radar_dir`, `sources_dir`, `log_path`, `insights_dir`) — вне
контура ktalk (не используются ни одним из 11 файлов таблицы RES-001) — в `.ktalk.toml` не
переносятся, `vault-config.md` остаётся их единственным источником.

### Порядок относительно апгрейда пакета

ADR-013-spec (бриф Dev, «Обязательное условие переключения на новый дефолт») уже зафиксировал:
первый запуск после апгрейда пакета на версию с машинным дефолтом (FR-22) без явно объявленного
пути молча уйдёт на новый дефолт. Порядок для vault'а `naumen-cto`, обязательный:

1. Создать `.ktalk.toml` на корне vault'а с `registry.db_path = "95_TRANSCRIPTS/.registry.db"`
   (и полной таблицей маршрутизации выше) — **до** апгрейда пакета.
2. Проверить `ktalk config show --json` на текущей (доапгрейдной) версии пакета: файл читается,
   `db_path` резолвится в тот же путь, что и сегодняшний дефолт `config.py` — регрессия перед
   апгрейдом, не после.
3. Только после шага 2 — апгрейд `ktalk-mcp` до версии, реализующей FR-20/22/23 (0.7.0).
4. После апгрейда — тот же прогон `ktalk config show --json`/`ktalk auth-status`, сверка, что
   путь БД не изменился (NFR-11 AC1).

Этот порядок — предпосылка cutover-процедуры ADR-012-spec (шаг 3 «создать конфиг раскладки»): там
шаг создания конфига описан безотносительно к версии пакета, здесь уточняется, что для живого
vault'а этот шаг обязан предшествовать апгрейду пакета по времени, не просто предшествовать
удалению файлов-копий агентов (шаг 4 той процедуры). `vault-config.md` не удаляется этим шагом —
остаётся человекочитаемым описанием, `.ktalk.toml` становится входом для кода.

## Компоненты

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|-----------------|-------|--------|-------------|
| `host_config.py` (новый модуль) | Discovery + парсинг + валидация `.ktalk.toml` | `${CLAUDE_PROJECT_DIR}`, `cwd` | `HostConfig \| None`, либо `HostConfigError` | `tomllib` (stdlib) |
| `resolve_db_path` (расширение `config.py`, ADR-013-spec) | Приоритет источников пути реестра | `--db`, `KTALK_REGISTRY_DB`, `HostConfig.registry.db_path`, машинный дефолт | `Path` | `host_config.py` (получает уже готовый `HostConfig`, не делает discovery сам) |
| `ktalk config show` (CLI, новая подкоманда) | Печать резолвленного конфига машинно/человекочитаемо | discovery-результат | markdown или JSON в stdout | `host_config.py` |
| Шаги skill/agent (плагин, вне пакета) | Подстановка плейсхолдеров в шаблон маршрута, явная пометка отсутствующих ключей | вывод `ktalk config show --json`, значения `{date}`/`{id}`, вычисленные промтом | путь файла артефакта или явная пометка недоступности | вызов CLI инструментом Bash |

## Границы

- `host_config.py` не пишет файлы и не создаёт каталоги — только читает и валидирует.
- Подстановка плейсхолдеров (`{date}`, `{id}`, …) — не задача этого модуля и не задача
  `.ktalk.toml`; шаблон отдаётся как строка, конкретизация — на стороне промта.
- Обнаружение фактической доступности `qmd` (наличие MCP-инструмента в текущей сессии) — не
  задача `host_config.py`: `integrations.qmd` — только заявленное намерение хозяина, фактическая
  проверка — на стороне промта/агента в момент шага (FR-24).
- Слияние конфигов нескольких уровней каталогов — не реализуется (см. «Discovery», п.4).
- MCP-транспорт не участвует в discovery/маршрутизации (ADR-012 §2а) — `host_config.py`
  используется CLI-командой `ktalk config show` как единственным каналом для промтов; то, что
  MCP-сервер пакета технически тоже импортирует `config.py`/`resolve_db_path` для доступа к
  реестру записей, не делает MCP вторым путём discovery — маршрутизация (`routing`/`directories`)
  промтам через MCP не отдаётся вовсе, только через CLI.

## Интеграционные точки

| Точка | Протокол | Контракт | Auth | Rate limit | Error handling |
|-------|----------|----------|------|------------|----------------|
| `host_config.py` → `${CLAUDE_PROJECT_DIR}`/`cwd` | локальная ФС | discovery-алгоритм выше | н/п | н/п | `HostConfigError` с именем файла и причиной на невалидном TOML/схеме; отсутствие файла — не ошибка |
| `resolve_db_path` → `host_config.py` | in-process вызов | принимает готовый `HostConfig \| None`, не делает discovery | н/п | н/п | ADR-013-spec, не переопределяется здесь |
| Промт skill/agent → `ktalk config show --json` | subprocess (Bash tool) | JSON: `{registry: {db_path}, directories: {...}, routing: {...}, integrations: {...}}`, отсутствующий ключ = отсутствует в JSON, не `null` (различимо от «объявлено пустой строкой») | н/п (локальный процесс, не сеть) | н/п | ненулевой код возврата CLI при `HostConfigError` — промт обязан прочитать stderr и остановить шаг, не игнорировать код возврата |

## NFR Mapping

- `### Requirement: NFR-11` (совместимость с живым vault'ом) → раздел «Миграция vault'а на
  конфиг»: `.ktalk.toml` объявляет сегодняшнюю раскладку один в один, порядок «конфиг до
  апгрейда» снимает риск молчаливого перехода на новый дефолт.
- `### Requirement: NFR-16` (разграничение данных ktalk/хозяина) → `.ktalk.toml` не содержит
  секретов и не публикует пути централизованного хранилища (ADR-013) — только пути и маршруты
  артефактов хозяина; секреты остаются в env/`.mcp.json` хозяина (FR-25, вне периметра этой спеки).

## Контракт с QA-author

**Сценарии приёмки (полный список из capability-спеки FR-20/FR-21/FR-24):**
- FR-20 AC1–AC3 (конфиг есть → пути из него; конфига нет → машинный дефолт без ошибки; конфиг
  повреждён → именованная ошибка, не тихий откат).
- FR-21 AC1–AC2 (registry-команды и MCP read-инструменты работают без vault-раскладки).
- FR-24 AC1–AC2 (обе зависимости недоступны → явная пометка без остановки; одна доступна, другая
  нет → используется доступная, недоступная помечена).

**Архитектурный контекст для тестов:**
- Компоненты: `host_config.py` (discovery + парсинг + валидация), расширение `resolve_db_path`
  (`config.py`), `ktalk config show` (CLI).
- Trust boundaries: `.ktalk.toml` — untrusted файловый ввод (владелец хозяина, не пакета) до
  валидации `host_config.py`; после валидации — доверенный `HostConfig` для остального кода.
- Промты skill/agent (плагин) — вне периметра pytest пакета: их использование `ktalk config show
  --json` проверяется статически (grep текста промта на отсутствие захардкоженных путей — тот же
  приём, что GO-критерий 3 постановки волны для состава плагина, ADR-012-spec).

**Edge cases / boundary conditions:**
- `.ktalk.toml` существует, но пустой файл (валидный TOML, ноль ключей) — эквивалент «конфига
  нет» по каждому отдельному ключу, не ошибка.
- Неизвестный top-level ключ (например, опечатка `[routng]`) — `HostConfigError`, не тихое
  игнорирование неизвестной секции.
- `${CLAUDE_PROJECT_DIR}` задан, но `.ktalk.toml` по этому пути отсутствует — FR-20 AC2 (нет
  ошибки, машинный дефолт), обхода вверх при этом не происходит (см. «Discovery» п.1).
- Обход вверх (голый CLI без `${CLAUDE_PROJECT_DIR}`) упирается в `.git` до `.ktalk.toml` —
  остановка на границе `.git`, конфиг каталога-предка не подхватывается.
- `integrations.qmd = true` в конфиге, но MCP-инструмент `qmd` недоступен в реальной сессии —
  пометка недоступности всё равно происходит (заявление не заменяет факт).
- `directories.people` объявлен, каталог физически удалён/переименован — пометка «объявлен, но не
  существует», отличная от «не объявлен».

**Test-pyramid рекомендация:**

| Группа AC | Уровень | Обоснование |
|-----------|---------|-------------|
| FR-20 (discovery: есть/нет/повреждён, обход вверх/через `${CLAUDE_PROJECT_DIR}`) | unit + integration | парсинг/валидация — unit (чистая функция от содержимого файла); обход по реальной файловой иерархии (граница `.git`, несколько уровней) — integration на временных каталогах |
| FR-21 (registry-команды/MCP read без `.ktalk.toml`) | integration | CLI/MCP end-to-end во временном проекте без конфига — уже часть контракта QA-author ADR-012-spec, не дублируется здесь |
| FR-24 (деградация `qmd`/`directories.people`) | integration | реальная сессия с недоступным MCP-инструментом/удалённым каталогом на фикстуре |
| `ktalk config show` (JSON-контракт) | unit | сериализация `HostConfig` → JSON, отсутствующий ключ ≠ `null` |

## Бриф для Dev

**Архитектура:** этот документ + [ADR-012](../00-project/adr/ADR-012-plugin-boundary.md) +
[ADR-013](../00-project/adr/ADR-013-central-transcript-store.md) + [ADR-013-spec](ADR-013-central-transcript-store-spec.md).
**Требование:** [ktalk-plugin.md](../30-requirements/ktalk-plugin.md), FR-20, FR-21, FR-23, FR-24, NFR-11, NFR-16.
**Фаза:** Pilot (0.7.0).

**Реализовать:**
- `host_config.py` — новый модуль: `discover_host_config`, `load_host_config` (`tomllib`),
  `HostConfig` (dataclass/pydantic — на усмотрение Dev, без новой зависимости при dataclass),
  `HostConfigError`.
- Расширение `resolve_db_path` (`config.py`) — принимает `HostConfig | None` параметром (ADR-013-spec
  уже описывает четвёртый источник; здесь — откуда берётся значение параметра).
- `ktalk config show` (CLI, `_REGISTRY_FREE_COMMANDS`) — markdown/`--json` вывод `HostConfig`.
- Депараметризация промтов skill/agent (DEV-002, ADR-012-spec) — замена зашитых путей на вызов
  `ktalk config show --json` и явную пометку отсутствующих ключей по «Контракту деградации» выше.

**Порядок:** fixtures (валидный/пустой/повреждённый `.ktalk.toml`, вложенная иерархия каталогов с
`.git`-границей) → `host_config.py` → расширение `resolve_db_path` → `ktalk config show` →
депараметризация промтов (последней — зависит от готового CLI-вывода).

**Сценарии приёмки:** FR-20 AC1–AC3, FR-21 AC1–AC2, FR-23 AC1–AC3 (регрессия приоритета —
покрыта ADR-013-spec, здесь не дублируется), FR-24 AC1–AC2.
