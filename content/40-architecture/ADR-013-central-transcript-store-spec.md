# ADR-013 — спека: разрешение пути, детекция облачной синхронизации, миграция

Companion-спека к [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md). Детализация
реализации, брифы Dev/DevOps, контракт QA-author. Решение — в ADR, здесь — как оно исполняется.

## Контекст

FR-22/FR-23/FR-25, NFR-12–NFR-16 требуют: машинный дефолт хранилища, приоритет источников пути,
проверку конкурентного доступа, охрану от облачной синхронизации, права доступа, обратимую
миграцию. ADR-013 фиксирует решения; здесь — алгоритмы и контракты теста.

## Компоненты

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|-----------------|-------|--------|-------------|
| `resolve_db_path` (расширение `config.py`) | Разрешает путь реестра по приоритету §1 | `--db`, `KTALK_REGISTRY_DB`, путь из конфига хозяина (SA-003), машинный дефолт | `Path` | конфиг хозяина — модуль SA-003, не этот |
| `resolve_store_root` (новая функция, отдельный модуль — не `registry.py`) | Резолвит и создаёт корень централизованного хранилища | `$XDG_DATA_HOME`, `$HOME` | `Path` с гарантированными правами `0700` | ОС |
| `detect_sync_dir` (тот же модуль) | Эвристика: путь внутри известного каталога облачной синхронизации | резолвленный `Path` | `bool` + человекочитаемая причина | список известных маркеров (см. ниже) |
| Команда миграции (имя уточняет Dev, не `ktalk migrate <vault>`) | Копирует БД в централизованное хранилище, переименовывает источник в backup | путь-источник, путь-назначение | код возврата, лог построчной сверки | `registry.py` (read-only использование — дамп) |

Новый код не расширяет `registry.py` (грандфазер 562 строки) — путь, детекция синхронизации и
миграция живут в отдельном модуле (рабочее имя `store.py`), который импортирует `registry.py`
для операций с БД, а не наоборот.

## Границы

- Формат конфига проекта-хозяина и алгоритм discovery (снизу вверх от cwd) — SA-003, не эта
  спека. Здесь используется только выход SA-003: разрешённый путь БД, если конфиг его задаёт.
- Граница плагина, версионирование, канал доставки — SA-001 (ADR-012).
- Windows не проектируется — вне рамок волны.

## Поток данных

1. CLI/MCP стартует → `resolve_db_path(cli_db)`.
2. Источники проверяются по порядку: `cli_db` → `KTALK_REGISTRY_DB` → путь из конфига хозяина
   (если discovery SA-003 нашёл конфиг и в нём задан путь) → `resolve_store_root() / "registry.db"`.
   Путь из конфига хозяина (`host_config.registry.db_path`) резолвится по
   `Path(configured).is_absolute()`:
   - абсолютный путь используется как есть, каталог `.ktalk.toml` в резолюцию не участвует;
   - относительный путь джойнится с `host_config.path.parent` — каталогом, где обнаружен
     `.ktalk.toml` (SA-003 «Discovery»), не с cwd вызывающего процесса. `--db` и
     `KTALK_REGISTRY_DB` этой ветки не касаются: у них нет файла конфигурации как базы, резолюция
     от cwd для них остаётся конвенцией командной строки и окружения;
   - `host_config.path is None` при относительном `db_path` — нарушение инварианта вызывающей
     стороны: `discover_host_config` (SA-003) в проде всегда заполняет `path` у найденного
     конфига, ручная сборка `HostConfig` с относительным `db_path`, но без `path`, не даёт функции
     базы для join. `resolve_db_path` в этом случае поднимает исключение, не откатывается на
     резолюцию от cwd — молчаливый откат воспроизвёл бы именно тот дефект, который резолюция от
     `.ktalk.toml` устраняет.
3. Первый непустой источник побеждает, остальные не читаются (для `--db`/env — как сегодня; для
   конфига хозяина и дефолта — лениво, только если оба предыдущих отсутствуют).
4. Итоговый путь — уже полностью резолвленный (после join для относительного `db_path` из конфига
   хозяина, если применимо) — прогоняется через `detect_sync_dir` в этой же точке потока,
   одинаково независимо от источника. Если путь получен из машинного дефолта —
   проверка не имеет практического смысла (дефолт по конструкции вне известных каталогов
   синхронизации), но выполняется тем же кодом ради единообразия и как регресс-барьер, если
   дефолт когда-нибудь изменится. Если путь получен из `--db`/env/конфига хозяина и
   `detect_sync_dir` вернул `True` — предупреждение в stderr перед открытием БД, работа
   продолжается (NFR-14 не блокирует, только предупреждает).
5. Каталог хранилища создаётся при первом обращении с правами `0700`; файл БД — при первой записи
   SQLite с правами `0600` (обеспечивается `umask` процесса на момент создания, не post-hoc
   `chmod`, чтобы не было окна между созданием и ограничением прав).

## Интеграционные точки

| Точка | Протокол | Контракт | Auth | Rate limit | Error handling |
|-------|----------|----------|------|------------|----------------|
| `resolve_db_path` → конфиг хозяина (SA-003) | вызов функции in-process | принимает `Path \| None` от discovery-модуля SA-003 | н/п | н/п | discovery-модуль сам отвечает за диагностику повреждённого конфига (FR-20 AC3); `resolve_db_path` не валидирует содержимое, только использует результат |
| Команда миграции → `registry.py` | in-process, чтение через существующий `sqlite3`-слой | построчный дамп источника == построчный дамп назначения после копирования | н/п | н/п | несовпадение дампа → отказ команды, источник не переименовывается |

## NFR Mapping

- `### Requirement: NFR-11` (совместимость с живым vault'ом) → приоритет §3 гарантирует: пока
  конфиг хозяина не задаёт путь и `KTALK_REGISTRY_DB`/`--db` не заданы явно, машинный дефолт
  вступает в силу — но живой vault сегодня фактически задаёт путь через существующий
  `95_TRANSCRIPTS/.registry.db`-дефолт `config.py`, который заменяется машинным; для сохранения
  сегодняшнего пути на переходный период vault обязан объявить его явно через конфиг хозяина
  (SA-003) или `KTALK_REGISTRY_DB` — без этого шага NFR-11 AC2 нарушается переходом на новый
  дефолт. **Это явное требование к моменту переключения, не автоматическая совместимость** —
  фиксируется как условие в брифе Dev ниже.
- `### Requirement: NFR-12` (миграция — явный шаг) → отдельная команда (не побочный эффект
  установки), copy-then-backup семантика, построчная сверка дампа перед переименованием источника.
- `### Requirement: NFR-13` (конкурентный доступ) → WAL+`busy_timeout` не меняется; обеспечивается
  тестовым контрактом ниже (доказательство, не новый механизм).
- `### Requirement: NFR-14` (облачная синхронизация) → `detect_sync_dir`, эвристика ниже.
- `### Requirement: NFR-15` (права доступа) → `0700`/`0600` при создании, `umask`-контролируемо.
- `### Requirement: NFR-16` (разграничение данных) → раскладка §2 ADR: только `registry.db`,
  `transcripts/`, `eval/reports/`; протоколы/`registry.md`/профили никогда не пишутся в
  централизованный корень — по построению (эти артефакты формируются кодом, не адресующим
  корень хранилища).

## Детекция облачной синхронизации (NFR-14)

Платформенного API, дающего окончательный ответ, нет (RES-001, тема 2) — эвристика, не гарантия.

**Маркеры (path содержит любой из сегментов, регистронезависимо):**
- macOS: `Library/Mobile Documents` (iCloud Drive), `Dropbox`, `Google Drive`, `OneDrive`,
  `Library/CloudStorage` (унифицированный каталог провайдеров начиная с современных macOS).
- Linux: `Dropbox`, `Nextcloud`, `ownCloud`, `Google Drive`, `OneDrive` — по имени каталога, так
  как единого системного соглашения на Linux нет (клиенты монтируют произвольно).
- Общее: если `$HOME/Documents` целиком синхронизируется (macOS «Desktop & Documents» в iCloud)
  — путь резолвится ОС в `~/Library/Mobile Documents/com~apple~CloudDocs/Documents/...`, что уже
  покрывается первым маркером; отдельная проверка симлинка не нужна.

**Известное ограничение:** RES-001 находка 11 — на исследуемой машине `~/Documents` не под
синхронизацией, поведение эвристики под реальной iCloud/Dropbox-синхронизацией не проверено
прямым экспериментом. Ложноотрицательный случай — нестандартный путь монтирования облачного
клиента, не входящий в список маркеров. Список — конфигурируемый в коде, не расширяется по
запросу пользователя в рантайме.

**Поведение при срабатывании:** только если путь получен НЕ из машинного дефолта (§1 ADR) —
предупреждение в stderr с именем обнаруженного маркера и путём, операция продолжается (NFR-14
AC2 — предупреждение, не блокировка).

## Контракт теста конкурентного доступа (NFR-13)

Что обязано быть доказано, не предположено:

1. Два независимых процесса (не потока — процесса, эмулирующих два разных проекта-хозяина)
   открывают один и тот же файл БД одновременно и параллельно выполняют `mark-*`/`sync`-подобные
   транзакции. После завершения обоих: `PRAGMA integrity_check` возвращает `ok`, ни одна ранее
   существовавшая запись не потеряна.
2. Конфликт на одной и той же записи (один процесс — `done`, другой одновременно — `skipped` для
   того же ключа): итоговое состояние равно ровно одному из двух значений, определяемому порядком
   завершения транзакций (детерминированно post-hoc, не предсказуемо заранее) — не пустому, не
   смешанному, не повреждённому.
3. При исчерпании `busy_timeout=5000` — процесс получает `sqlite3.OperationalError` с текстом,
   узнаваемым как «занято» (не тонет в обобщённом traceback), а не тихо теряет операцию.

**Что НЕ входит в контракт:** тест не проверяет производительность под высокой конкуренцией
(число параллельных процессов сверх двух), не проверяет поведение при сетевой ФС (только
локальный POSIX том) — вне рамок NFR-13.

**При конфликте (эксплуатационное поведение, не тест):** ответственность на вызывающей стороне —
CLI/навык получает понятную ошибку и штатно ретраит операцию (существующее поведение `busy_timeout`
уже ретраит на уровне SQLite до 5с; выше этого — не новый механизм, а штатный отказ операции).

## Контракт команды миграции (NFR-12)

Рабочее имя команды уточняет Dev при реализации (не `ktalk migrate <vault>` — тот уже занят
импортом markdown-архивов по ADR-002).

**Инварианты:**
- Команда не запускается неявно установкой плагина или первым запуском — только явным вызовом
  (NFR-12 AC1).
- Источник (`95_TRANSCRIPTS/.registry.db` или путь, заданный конфигом/`KTALK_REGISTRY_DB`) не
  удаляется и не изменяется до завершения проверки: копия делается на целевой путь (§2 ADR), затем
  построчная сверка дампа источник↔копия (все таблицы, все колонки, без исключений).
- Сверка не совпала → команда завершается ошибкой, источник остаётся без изменений, целевой файл
  удаляется (не остаётся частичной копией).
- Сверка совпала → источник переименовывается в backup-суффик (например,
  `.registry.db.pre-migration-<дата>`), не удаляется. С этого момента централизованный файл —
  единственный, который открывают команды реестра (через приоритет §3 ADR — источник больше не
  адресуется дефолтом).
- Откат — задокументированные шаги в runbook (OPS-001), не автоматическая команда: переименовать
  backup обратно, указать путь явно через `--db`/`KTALK_REGISTRY_DB`/конфиг до следующего запуска.
  Если после миграции в централизованный файл добавлялись записи от другого проекта — руководство
  явно называет это известным ограничением отката (частичная потеря новых записей другого проекта
  при откате единственного), NFR-12 AC3 требует только наличие и выполнимость шагов, не
  автоматизацию без потерь в этом кросс-проектном случае.

## Бриф для Dev

**Архитектура:** [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md) + эта спека
**Требование:** FR-22, FR-23, FR-25, NFR-12–NFR-16
**Фаза:** Pilot (0.7.0)

**Реализовать:**
- Новый модуль (не `registry.py`): `resolve_store_root`, `detect_sync_dir`, права `0700`/`0600`
  при создании.
- Расширение `resolve_db_path` (`config.py`) четвёртым источником между env и дефолтом — приоритет
  §3 ADR; сигнатура принимает разрешённый конфигом хозяина путь как параметр (сам discovery — вне
  этой задачи, SA-003/DEV-001).
- Команда миграции: copy → сверка дампа → backup-переименование источника; отдельно от
  `ktalk migrate <vault>`.
- **Обязательное условие переключения на новый дефолт (см. NFR Mapping → NFR-11 выше):** до
  релиза, меняющего дефолт БД, живой vault обязан получить явно заданный путь (конфиг хозяина
  или `KTALK_REGISTRY_DB`) — иначе первый же запуск после апгрейда пакета в vault'е молча начнёт
  писать в новый машинный дефолт вместо `95_TRANSCRIPTS/.registry.db`. Порядок выкатки — задача
  DevOps/OPS-001, не молчаливое допущение Dev.

**Порядок:** fixtures (два процесса, повреждённый/валидный дамп, путь внутри/вне маркеров
синхронизации) → интерфейсы (`resolve_store_root`, `detect_sync_dir`, сигнатура миграции) →
реализация → тесты.

**Сценарии приёмки:** см. «Контракт с QA-author» ниже — полный список из требования.

## Бриф для DevOps

**Архитектура:** [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md)

**Подготовить:**
- Runbook (OPS-001): установка плагина/пакета в проект без vault-раскладки, миграция живого
  vault'а на централизованное хранилище, откат — шаги из раздела «Контракт команды миграции»
  выше, с явным предупреждением про кросс-проектный кейс отката.
- Порядок выкатки релиза, меняющего дефолт БД: живой vault получает явный путь (конфиг/env) ДО
  апгрейда пакета — иначе риск молчаливого расхождения реестра (см. NFR-11 в NFR Mapping).
- Мониторинг: нет метрик рантайма в этой волне (CLI/локальный процесс, не сервис) — только
  runbook-проверка `PRAGMA integrity_check` после миграции и после инцидентов конкурентного
  доступа.

**NFR из BA:** NFR-12 (миграция обратима), NFR-13 (конкурентный доступ доказан тестом, не
предположением), NFR-14 (не под облачной синхронизацией молча), NFR-15 (права доступа владельца),
NFR-16 (разграничение данных ktalk/хозяина).

## Контракт с QA-author

**Сценарии приёмки (полный список из capability-спеки FR-22/FR-23/NFR-12–NFR-16):**
- Given проект не задаёт `--db`/`KTALK_REGISTRY_DB`/конфиг хозяина, реестр резолвится в машинный
  дефолт вне cwd (FR-22 AC1).
- Given два проекта без собственного пути, оба адресуют один и тот же файл (FR-22 AC2).
- Given хранилище создаётся впервые, права ограничивают доступ владельцем (FR-22 AC3 / NFR-15).
- Given все четыре источника заданы одновременно, применяется `--db` (FR-23 AC1).
- Given `--db` не задан, применяется `KTALK_REGISTRY_DB` (FR-23 AC2).
- Given только конфиг хозяина задаёт путь, применяется он, не машинный дефолт (FR-23 AC3).
- Given `registry.db_path` в конфиге хозяина задан относительным путём, реестр открывается из
  каталога, отличного от каталога `.ktalk.toml` (включая подкаталог хранилища), путь резолвится
  относительно каталога `.ktalk.toml`, не относительно cwd (FR-23 AC4).
- Given `registry.db_path` в конфиге хозяина задан абсолютным путём, путь применяется как есть,
  каталог `.ktalk.toml` в резолюцию не участвует (FR-23 AC5).
- Given установлен плагин без вызова команды миграции, файл реестра остаётся на прежнем пути
  (NFR-12 AC1).
- Given команда миграции завершена успешно, все записи присутствуют в целевом расположении без
  потерь и без изменения значений (NFR-12 AC2).
- Given требуется откат, шаги в runbook существуют и выполнимы (NFR-12 AC3, ручная проверка).
- Given два процесса параллельно пишут в общий файл, обе операции завершаются успешно или понятной
  ошибкой занятости, без повреждения БД (NFR-13 AC1).
- Given конкурентная запись затрагивает одну и ту же запись реестра, итоговое состояние — ровно
  одно из двух значений (NFR-13 AC2).
- Given резолвленный дефолт проверяется относительно каталогов синхронизации, он вне них
  (NFR-14 AC1).
- Given пользователь явно указывает путь внутри распознаваемого каталога синхронизации, он
  получает предупреждение, не блокировку (NFR-14 AC2).
- Given хранилище создано, права каталога/файлов — `0700`/`0600` (NFR-15 AC).
- Given выполнен `export`, зеркало создаётся в проекте-хозяине, не в централизованном хранилище
  (NFR-16 AC).
- Given `export` вызван без `--out`, без `--db`, без `KTALK_REGISTRY_DB` и без `.ktalk.toml` —
  то есть БД резолвится к машинному дефолту, — проектом-хозяином считается `CLAUDE_PROJECT_DIR`,
  если он задан, иначе текущий рабочий каталог. Это тот же контракт, по которому проект-хозяина
  определяет `discover_host_config` (`host_config.py`), и он назван здесь явно: прежняя редакция
  требовала «в проект-хозяина», но при голом вызове CLI не говорила, что им считать, и
  реализация клала зеркало рядом с БД — то есть внутрь хранилища, против этого же NFR-16
  (найдено сверкой спек с кодом, эпик `ktalk-plugin-56l`, ратифицировано владельцем 2026-08-31).

**Архитектурный контекст для тестов:**
- Компоненты: `resolve_db_path` (`config.py`), `host_config.py` (SA-003, отдаёт `HostConfig.path`
  как базу join для относительного `db_path`), новый модуль хранилища (`resolve_store_root`,
  `detect_sync_dir`), команда миграции, `registry.py` (используется, не расширяется).
- Интеграции: файловая система (права, симлинки для эвристики синхронизации, join относительного
  `db_path`), два ОС-процесса для NFR-13 (не потоки — реальный `subprocess`/`multiprocessing` с
  раздельными открытиями БД).
- Trust boundaries: CLI-флаг/env — доверенный ввод пользователя; конфиг хозяина — untrusted до
  валидации SA-003 (эта спека потребляет уже провалидированный путь и провалидированный
  `HostConfig.path`).

**Edge cases / boundary conditions:**
- `$XDG_DATA_HOME` задан пустой строкой vs не задан вовсе — разное поведение `os.environ.get`.
- Путь из конфига хозяина указывает на несуществующий родительский каталог — создаётся или падает
  явной ошибкой (решение — Dev, тест должен зафиксировать выбранное поведение, не мимо него).
- Относительный `db_path` при обходе вверх от cwd (discovery-режим 2, SA-003): найденный
  `.ktalk.toml` лежит не там, откуда запущена команда, — база join берётся из каталога находки, не
  из cwd команды; это сценарий, воспроизводящий исходный симптом дефекта (`unable to open database
  file` при запуске из подкаталога).
- Относительный `db_path` при явном `project_dir`/`CLAUDE_PROJECT_DIR` (discovery-режим 1): база
  join — тот же каталог, что и явно переданный корень, обход не выполняется.
- `resolve_db_path` вызван напрямую (не через `discover_host_config`) с вручную собранным
  `HostConfig(registry={"db_path": "относительный/путь"}, path=None)` — ожидаемое исключение, не
  тихий откат на резолюцию от cwd.
- Миграция при уже существующем файле по целевому пути (повторный вызов команды) — не должна тихо
  перезаписать более новые данные централизованного хранилища.
- `busy_timeout` исчерпан — ошибка узнаваема, не generic traceback.
- Эвристика синхронизации: путь содержит маркер как подстроку имени, но не как сегмент пути
  (например, каталог `MyDropboxBackup/` не должен ложно сработать на `Dropbox`) — граница
  сегментации маркера.
