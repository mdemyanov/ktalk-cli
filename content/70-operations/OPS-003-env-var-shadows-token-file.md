# OPS-003: Переменная окружения перекрывает файл токена

**Опоры:** `src/ktalk_cli/config.py`, `src/ktalk_cli/token_file.py`, `README.md` («Порядок источников»), `openspec/specs/talk-api-auth-modes/spec.md`

## Purpose

Использовать, когда токен обновлён, а `ktalk` продолжает получать отказ авторизации:
`ktalk auth-status` печатает `alive: false` сразу после успешной записи свежего токена,
`ktalk token status` при этом показывает `usable: true`. Класс отказа — **переменная
`KTALK_SESSION_TOKEN` в стартовом файле оболочки перекрывает файл токена и переживает его
ротацию**: `ktalk token set` пишет в файл, которого процесс не читает.

Отказ выглядит как протухший токен и чинится повторной записью токена — безрезультатно,
сколько бы раз её ни повторили. Замер: час диагностики у автора пакета (2026-09-08).

Не путать с [OPS-002](OPS-002-single-auth-mode-transition.md) — та процедура про снятую
переменную `KTALK_PERSONAL_API_KEY` и переход между режимами; здесь режим один, и мешает
не он, а порядок источников внутри него.

## Почему так устроено

Порядок источников — первый непустой выигрывает ([README](../../README.md) «Порядок
источников», сценарии `Session env var takes priority over the token file` и `Token file is
the fallback of last resort` в `openspec/specs/talk-api-auth-modes/spec.md`):

| # | Источник |
|---|---|
| 1 | `KTALK_SESSION_TOKEN` — окружение или `.env` рабочего каталога |
| 2 | `~/.config/ktalk-mcp/token` |

Файл читается валидатором `Settings` **только когда переменная пуста**
(`src/ktalk_cli/config.py`, `_fall_back_to_token_file`). Приоритет сам по себе верен —
заданное явно сильнее лежащего на диске. Ловушка в другом: `ktalk token set` пишет во
второй источник, ничего не зная про первый, и **не предупреждает**, что записанное значение
не будет прочитано. Ротация ключа проходит успешно и не меняет ничего.

## Задет ли ты

Без сети и без вывода значения в терминал (утечка секрета — красная линия):

```bash
if [ -n "${KTALK_SESSION_TOKEN:-}" ]; then
  echo "затронуты: KTALK_SESSION_TOKEN задана — она перекрывает файл токена"
else
  echo "не затронуты: KTALK_SESSION_TOKEN не задана, читается файл"
fi
```

Фактический вывод в сеансе публикации рунбука (машина владельца, отказ активен):
```
затронуты: KTALK_SESSION_TOKEN задана — она перекрывает файл токена
```

**Не используйте** `echo "${KTALK_SESSION_TOKEN:-не задана}"` для той же цели — при заданной
переменной оболочка подставит само значение секрета, а не текст по умолчанию (`:-` —
fallback на пустую переменную, не проверка условия). Та же ошибка уже зафиксирована в
[OPS-002](OPS-002-single-auth-mode-transition.md) «Known problems».

## Диагностика: развести источники

Ключевой шаг — сравнить два вызова, отличающихся ровно наличием переменной. `env -u`
снимает её на один вызов, ничего не меняя в системе:

```bash
ktalk auth-status --json                          # как обычно: источник — переменная
env -u KTALK_SESSION_TOKEN ktalk auth-status --json   # тот же вызов, источник — файл
```

Фактические выводы в сеансе публикации (значения токенов и домен в ответах не фигурируют):

```json
// из переменной
{ "alive": false, "note": "Токен сессии не прошёл проверку (пробный запрос списка записей)." }
```
```json
// из файла
{ "alive": true, "note": "У сессионного токена нет понятия scope/срока действия — выполнена пробная проверка list_recordings(top=1), а не имитация без сети." }
```

Коды возврата процесса, замеренные отдельно (без пайпа — `$?` после пайпа вернёт код
последней команды пайпа, не `ktalk`):

| Вызов | `alive` | exit |
|---|---|---|
| `ktalk auth-status --json` | `false` | `1` |
| `env -u KTALK_SESSION_TOKEN ktalk auth-status --json` | `true` | `0` |
| `ktalk doctor --json` | — | `1` |
| `env -u KTALK_SESSION_TOKEN ktalk doctor --json` | — | `0` |

**Расхождение между этими двумя строками — и есть диагноз.** Совпадение (`false` в обоих)
означает другую причину: токен в файле тоже мёртв, читайте раздел «Если развести не
получилось».

`ktalk doctor --json` даёт ту же картину одним вызовом — поле `auth.alive` и список
`failed_items`. Фрагмент фактического вывода в сеансе публикации (**домен заменён
плейсхолдером** — боевое значение в документацию не переносится):

```json
{
  "token_file": { "path": "/Users/<you>/.config/ktalk-mcp/token", "present": true,
                  "mode": "0600", "usable": true },
  "auth": { "alive": false,
            "note": "Токен сессии не прошёл проверку (пробный запрос списка записей)." },
  "workspace": { "base_url": "https://your-domain.ktalk.ru", "source": "env:KTALK_BASE_URL" },
  "host_config": { "status": "absent" },
  "ok": false,
  "failed_items": ["auth"]
}
```

Сочетание `token_file.usable: true` при `auth.alive: false` — тот самый отпечаток: файл
исправен и читаем, но не он отвечает на вопрос об авторизации.

## Лечение

**1. Найти, где переменная объявлена.** Она переживает перезапуск терминала, значит лежит в
стартовом файле оболочки, а не выставлена руками:

```bash
grep -rn "KTALK_SESSION_TOKEN" ~/.zshenv ~/.zshrc ~/.zprofile ~/.bash_profile ~/.bashrc 2>/dev/null | cut -d: -f1,2
grep -rn "KTALK_SESSION_TOKEN" .env 2>/dev/null | cut -d: -f1,2
```

`cut` оставляет файл и номер строки, отрезая само значение — grep без него напечатает
секрет в терминал и в историю.

`~/.zshenv` — самый частый и самый неочевидный дом: в zsh он читается для **любой**
оболочки, включая неинтерактивные вызовы из cron, systemd и редактора, поэтому переменная
из него действует там, где `~/.zshrc` уже не читается.

**2. Убрать строку.** Файловый шаг без команды пакета — `ktalk` эту переменную не создаёт и
не удаляет, только читает. Отредактируйте найденный файл и удалите (или закомментируйте)
строку `export KTALK_SESSION_TOKEN=...`. Значение переносить в файл токена не нужно: оно
отозвано, ради чего ротация и делалась.

**3. Снять переменную в текущей сессии.** Правка стартового файла не действует на уже
запущенную оболочку:

```bash
unset KTALK_SESSION_TOKEN
```

Для остальных открытых окон терминала — перезапустить их или выполнить `unset` в каждом.

**4. Убедиться, что в файле лежит актуальный токен.**

```bash
ktalk token status --json
```

Фактический вывод в сеансе публикации:
```json
{"path": "/Users/<you>/.config/ktalk-mcp/token", "present": true, "mode": "0600", "usable": true}
```
`usable: false` при `present: true` — файл пуст либо права шире `0600`; чинить
`chmod 600 <path>`, путь взять из поля `path` того же JSON. Если токен в файле устарел —
записать свежий: `pbpaste | ktalk token set -` (macOS), `xclip -o | ktalk token set -`
(Linux/X11); получение значения — [README](../../README.md), раздел «Session token».

**5. Проверить результат.**

```bash
ktalk auth-status --json ; echo "exit=$?"
```

Ожидается `alive: true` и `exit=0`. Тот же вызов через `env -u KTALK_SESSION_TOKEN` обязан
дать теперь **тот же** ответ — совпадение подтверждает, что переменной больше нет и оба
пути ведут к файлу.

**6. Проверить, что лечение переживёт перезапуск.** Новое окно терминала, затем шаг «Задет
ли ты» — ожидается ветка «не затронуты». Без этого шага правка стартового файла не отличима
от `unset` в одной сессии, и отказ вернётся завтра.

## Если развести не получилось

`alive: false` в обеих ветках диагностики — переменная ни при чём:

- Токен в файле тоже отозван или протух: повторить шаг 4 со свежим значением из браузера.
- `token status` даёт `usable: false` — чинить права (`chmod 600`) до сетевых проверок.
- `auth-status` даёт `alive: true`, но конкретная команда всё равно отказывает: это не
  авторизация, а права сессии на операцию — 403 читается как рабочий токен, `exit 0`, и
  перевыпуск токена ничего не изменит ([README](../../README.md), «Диагностика авторизации»).
- Отказала именно `ktalk list-archive` — операция не имеет пути под сессией ни при каком
  токене (профиль `None` в `OPERATION_PROFILES`), отказ до сети, код возврата `1`.

## Профилактика

- Держать токен **только** в файле. Переменная имеет смысл для CI и разовых прогонов
  (`KTALK_SESSION_TOKEN=... ktalk auth-status`), где она живёт ровно один вызов и никого не
  переживает; в стартовом файле оболочки она превращается в невидимый перехват ротации.
- После каждой ротации токена — шаг 5 этой процедуры, оба вызова. Одна строка, ловит весь
  класс отказа.

## Monitoring

CLI-инструмент, не сервис — рантайм-метрик нет (прецедент
[OPS-001](OPS-001-registry-migration-rollback.md) «Monitoring»).

- `ktalk doctor --json` → `ok` и `failed_items`; ненулевой код возврата — единственный
  встроенный сигнал для собственного cron/health-check (замерено: `1` при отказе `auth`,
  `0` при исправном состоянии).
- Значение токена не должно попадать в вывод, логи и алерты, собранные вокруг команд выше:
  барьер маскирования (`redact_secrets`) не отменяет дисциплины того, кто настраивает алерт.

## Escalation

On-call — оператор, выполняющий ротацию (пакет локальный, дежурства нет; прецедент OPS-001).
Эскалировать, если после шага 6 `alive: false` возвращается на следующем запуске оболочки:
значит переменная объявлена ещё в одном месте, не покрытом grep шага 1 (профиль оболочки,
отличной от zsh/bash; менеджер сессий; `launchctl setenv` на macOS; конфигурация IDE или
терминала, задающая окружение вне стартовых файлов).

## Known problems

- **`ktalk token set` не предупреждает, что записанное не будет прочитано.** Корень отказа:
  запись в файл и чтение из переменной не знают друг о друге. Процедурная компенсация —
  шаг 5; поведение пакета этим рунбуком не меняется.
- **`$?` после пайпа не читает код возврата `ktalk`.** `ktalk auth-status --json | tail -3;
  echo $?` вернёт код `tail`, то есть `0` при любом исходе. Замерено при подготовке
  рунбука — первая попытка замера дала ложный `exit=0` на отказе. Мерить без пайпа либо
  через `${PIPESTATUS[0]}`.
- **`grep` по стартовым файлам печатает секрет.** Формы в шаге 1 приведены с `cut -d: -f1,2`
  именно поэтому.
