# OPS-002: Переход на единственный режим авторизации (снятие персонального API-ключа)

**Опоры:** `content/00-project/adr/ADR-025-single-auth-mode.md`, `content/40-architecture/ADR-025-single-auth-mode-spec.md`, `content/30-requirements/single-auth-mode.md`, `src/ktalk_cli/token_file.py`, `src/ktalk_cli/cli_token.py`

## Purpose

Использовать при обновлении пакета до **3.0.0** ([ADR-025](../00-project/adr/ADR-025-single-auth-mode.md),
[«Единственный режим авторизации»](../30-requirements/single-auth-mode.md), FR-42…FR-44, NFR-18,
issue [mdemyanov/ktalk-cli#10](https://github.com/mdemyanov/ktalk-cli/issues/10)) — тем, кто сегодня
держит `KTALK_PERSONAL_API_KEY` в окружении. 3.0.0 не читает эту переменную ни на одном шаге: после
обновления она молча перестаёт что-либо значить, если авторизация не переведена на сессионный токен
заранее. Не путать с [OPS-001](OPS-001-registry-migration-rollback.md) — та процедура про
местоположение файла реестра, эта — про credential.

На момент публикации этого рунбука 3.0.0 не смержена в `main` этого дерева (ветка волны,
`pyproject.toml` показывает `2.1.0`) — шаги диагностики (раздел «Задет ли ты») и установки токена
(раздел «Переход») исполнимы уже сегодня на 2.1.0, шаги, зависящие от снятия ключа (громкий отказ
`list-archive`, новая форма `auth-status --json`), актуальны с момента выхода 3.0.0 — помечено по
месту.

## Preconditions

- `ktalk` в PATH (`uv run ktalk --version` — проверено в этом сеансе, ответ `ktalk-cli 2.1.0`).
- Доступ к вкладке браузера с активной сессией `https://<ваш-домен>.ktalk.ru`, залогиненной.
- Доступ к терминалу той же машины, где `ktalk` фактически исполняется (файл токена — локальный,
  не синхронизируется между машинами).
- Если переход делается заранее, до обновления пакета: текущая версия `ktalk` умеет
  `ktalk token set`/`ktalk auth-status` уже на 2.1.0 (команды не новые, ADR-025 их не меняет по
  форме вызова) — обновление пакета не блокирует подготовку.

## Задет ли ты

Проверяемо без сети, без чтения значения переменной в вывод (утечка секрета — красная линия):

```bash
if [ -n "${KTALK_PERSONAL_API_KEY:-}" ]; then
  echo "затронуты: KTALK_PERSONAL_API_KEY задана — читайте «Переход» и «Цена перехода» ниже"
else
  echo "не затронуты: KTALK_PERSONAL_API_KEY не задана, переход не требуется"
fi
```

Проверено в этом сеансе: без переменной — `не затронуты: ...`; с синтетическим значением
(`KTALK_PERSONAL_API_KEY=dummyvalue123`) — `затронуты: ...`, само значение в вывод не попало.

**Не используйте** форму `echo "${KTALK_PERSONAL_API_KEY:-не задана}"` для этой же цели — при
заданной переменной bash подставит само значение, не текст по умолчанию (`:-` — не проверка
условия, а fallback только на пустую/неустановленную переменную). Проверено экспериментом в этом
сеансе — форма выше свободна от этой ошибки.

## Переход

**1. Получить сессионный токен браузера.** На вкладке, где вы залогинены в Толк, DevTools (`F12`)
→ Console:

```js
copy(JSON.parse(localStorage.session).data.token)
```

UI-шаг открытия DevTools — нет CLI-эквивалента (браузерная консоль); проверено по актуальному
README (раздел «Session token») на 2026-09-08.

**2. Записать токен в файл.**

```bash
pbpaste | ktalk token set -          # macOS
xclip -o | ktalk token set -         # Linux (X11)
```

Не выполнено повторно в этом сеансе — команда перезаписала бы боевой токен, которым пользуется эта
же машина прямо сейчас. Механизм не меняется ADR-025 (правки таблицы файлов ADR-025-spec не
касаются `token_file.py`/`cli_token.py`) — читан по коду, не по памяти:
`token_file.write_token` пишет во временный файл правами `0600`, каталог `~/.config/ktalk-mcp/`
создаёт правами `0700`, переименовывает поверх (`os.replace`) — без окна, где секрет лежит с более
широкими правами. Значение короче 16 или длиннее 64 символов (не буквенно-цифровое) отклоняется до
записи с текстом ошибки, не называющим само значение.

**3. Проверить, что записалось (без сети).**

```bash
ktalk token status --json
```

Фактический вывод в этом сеансе (существующий рабочий токен этой машины):
```json
{"path": "/Users/mdemyanov/.config/ktalk-mcp/token", "present": true, "mode": "0600", "usable": true}
```
`usable: false` при `present: true` — файл пуст либо права шире `0600`; чинить
`chmod 600 <path>` (путь — из того же JSON, поле `path`).

**4. Проверить, что авторизация живая (сеть).**

```bash
ktalk auth-status --json
```

Фактический вывод в этом сеансе (2.1.0, `KTALK_PERSONAL_API_KEY` не задана, сессионный токен
рабочий):
```json
{
  "alive": true,
  "scopes": null,
  "expired_at": null,
  "note": "У сессионного токена нет понятия scope/срока действия — выполнена пробная проверка list_recordings(top=1), а не имитация без сети."
}
```
**После 3.0.0 форма ответа меняется** (ADR-025 п.3): поля `scopes`/`expired_at` удаляются из
`--json` целиком, остаётся `{"alive": bool, "note": str | None}`; код возврата процесса — `0` при
`alive: true`, `1` при `alive: false` (сегодня, на 2.1.0, код возврата безусловный `0` — не
проверять код возврата как признак отказа до обновления). Не проверено мной живьём на 3.0.0 — код
ADR-025 в этом дереве ещё не реализован (Dev работает в изолированной копии).

**5. Убрать `KTALK_PERSONAL_API_KEY` из окружения после подтверждённого перехода** — `.zshrc`/
`.bashrc`/`.env` проекта-хозяина, там, где переменная была заведена. UI/файловый шаг без единой
команды пакета — `ktalk` эту переменную не создаёт и не удаляет, только читает (до 3.0.0) или не
читает вовсе (с 3.0.0).

## Цена перехода (честно)

Персональный ключ был не капризом, а решением: он не привязан к браузерной сессии и не протухает
без предупреждения (README «Авторизация», issue #10). Сессионный токен — обратное свойство:
**он протухает молча**, и после снятия ключа компенсирующего постоянного режима не остаётся —
единственный доступный сегодня путь для непрерывной работы (демон, cron, CI) — ручное повторение
шагов «Переход» 1–3 по мере протухания, не автоматизировано пакетом.

Практическое следствие: если `ktalk` вызывается по расписанию (cron, systemd timer, фоновый
воркер), после перехода нужен ЛИБО ручной регламент обновления токена, ЛИБО собственный мониторинг
свежести (см. «Monitoring» ниже) — задача эксплуатации, не пакета. Владелец, ранее полагавшийся на
«настроил один раз ключ и забыл», теряет это свойство переходом безвозвратно, пока пакет не
предложит новый механизм (кандидатов сегодня нет — ADR-025 «Альтернативы» отклоняет резерв под
третий режим как YAGNI).

## Что перестаёт работать совсем

Замер (тестировано в этом сеансе, 2.1.0, таблица профилей ещё двухрежимная):

```bash
uv run python -c "
from ktalk_cli.endpoints import OPERATION_PROFILES
print([o for o,p in OPERATION_PROFILES.items() if not any(k.name=='SESSION' and v for k,v in p.items())])"
```

Вывод:
```
['list_archive', 'get_participants_full', 'get_participants_report']
```

Три операции таблицы без сессионного профиля — не три сломанные команды. Судьба каждой (ADR-025
§4, п.13 таблицы правок ADR-025-spec):

| Операция | CLI-команда | После 3.0.0 |
|---|---|---|
| `list_archive` | `ktalk list-archive` | **Перестаёт работать по-настоящему.** Отказывает до сети, детерминированно на каждый вызов, код возврата `1`. Уже сегодня, под сессией на 2.1.0, отказывает тем же способом (проверено в этом сеансе): `Ошибка: Операция «архив» доступна только в режиме персонального ключа (переменная KTALK_PERSONAL_API_KEY).`, `exit=1`. После 3.0.0 текст сообщения меняется на вариант без упоминания снятой переменной (`_profile_for`, ADR-025-spec п.8) — точная формулировка не проверена мной живьём, механизм (пре-сетевой отказ, код 1) гарантирован решением. |
| `get_participants_full` | `ktalk get-participants <recording_key>` | **Продолжает работать без изменений.** `get_full_participants` уже сегодня дообогащает результат безусловной session-веткой независимо от таблицы профиля (ADR-025 §4) — пользовательской потери нет. Не перепроверено мной на живой записи (нужен реальный `recording_key`) — утверждение из текста ADR-025, не из независимого прогона. |
| `get_participants_report` | нет — CLI-команды не существует (проверено: нет `add_parser`, нет записи в диспетчере `cli.py`) | **Ничего не меняется для пользователя.** Мёртвый код удаляется вместе с методом клиента — поверхности, с которой можно было столкнуться, не было. |

## Rollback (откат на 2.1.0)

Переход обратим — CLI не хранит состояние авторизации нигде, кроме файла токена и переменных
окружения; отката данных не требуется, только версии пакета.

1. Определить установленную версию — `uv run ktalk --version` (проверено в этом сеансе:
   `ktalk-cli 2.1.0`).
2. Откатить пакет на 2.1.0 (последняя версия с двумя режимами, `pyproject.toml` этого дерева на
   момент публикации рунбука):
   ```bash
   uv pip install "ktalk-cli==2.1.0"
   ```
   Не выполнено в этом сеансе (переустановка сломала бы локальное editable-окружение задачи) —
   проверено, что версия `2.1.0` фактически опубликована в PyPI (`pypi.org/pypi/ktalk-cli/json` →
   `releases` содержит `"2.1.0"`), команда синтаксически проверена (`uv pip install --help`,
   `uv 0.12.5`). Из исходников — тот же коммит доступен как `7b31e36` (merge, 2026-09-04,
   `pyproject.toml` → `2.1.0`): `git checkout 7b31e36 -- pyproject.toml uv.lock && uv sync`.
3. Проверка версии: `uv run ktalk --version` → ожидается `ktalk-cli 2.1.0`.
4. Вернуть `KTALK_PERSONAL_API_KEY` в окружение, если он использовался (шаг 5 «Перехода» его убрал)
   — 2.1.0 читает переменную снова, приоритет над сессией восстанавливается (README «Авторизация»,
   таблица источников).
5. Проверка успешности отката: `ktalk auth-status --json` (2.1.0, форма ответа с `scopes`/
   `expired_at`) отдаёт `alive: true` на рабочем credential — код возврата команды на 2.1.0
   безусловный `0`, не признак отката.

Откат не решает исходную причину волны (ADR-025 «Контекст»): конкуренция режимов и ложное «ключ
валиден» на 403 `access-info` возвращаются вместе с версией 2.1.0. Откатывать стоит только если
переход на сессионный токен создал операционную проблему серьёзнее этой (например, недоступность
ручного обновления токена для конкретного сценария автоматизации).

## Диагностика

`ktalk auth-status --json`/`ktalk token status --json` (использованы в шагах «Переход» 3–4) —
единственные диагностические команды, доступные в этом дереве сегодня.

Сводная команда `ktalk doctor` (issue [#14](https://github.com/mdemyanov/ktalk-cli/issues/14),
FR-48, [ADR-026](../00-project/adr/ADR-026-diagnostics-and-refusal-completeness.md)) готовится —
**в этом дереве её код не существует** (Dev волны 3 пишет её в изолированной копии, сюда не
влит). По решению ADR-026 она объединит те же четыре факта одним вызовом: пригодность файла
токена, живость сессии (тот же пробный запрос, что `auth-status`), состояние `.ktalk.toml`,
версию пакета — с ненулевым кодом возврата, только если хотя бы один пункт реально провален.
Пример JSON-вывода намеренно не приводится: у меня нет исполненной команды, а перенос
правдоподобной догадки без падающего носителя — уже задокументированный дефект этого проекта
(`content/lessons-learned.md`, запись 2026-09-07). Когда `ktalk doctor` появится в дереве — этот
раздел дополняется фактическим выводом, не раньше.

## Monitoring

CLI-инструмент, не сервис — рантайм-метрик нет ([OPS-001](OPS-001-registry-migration-rollback.md)
«Monitoring» устанавливает тот же прецедент для пакета).

- Проверка: `ktalk auth-status --json` → поле `alive` — норма `true`; после 3.0.0 код возврата
  процесса тоже сигнализирует отказ (`1` при `alive: false`, ADR-025 п.3) — для тех, кто ставит
  `ktalk auth-status` в собственный cron/health-check фоновой автоматизации (см. «Цена перехода»),
  это единственный встроенный сигнал протухания токена; частота опроса — по регламенту
  эксплуатации, пакет её не диктует.
- Проверка: `ktalk token status --json` → поле `usable` — `false` сигнализирует испорченный или
  отсутствующий файл токена раньше, чем это проявится сетевым отказом.
- Секреты (значение токена, значение `KTALK_PERSONAL_API_KEY`) не должны появляться в выводе,
  логах или мониторинговых алертах, собранных вокруг команд выше — барьер маскирования
  (`redact_secrets`, ADR-025-spec п.2) не заменяет дисциплину того, кто настраивает алерт: не
  прокидывать сырой stderr процесса без фильтрации в систему, где к логу шире доступ, чем к
  секрету. Политика хранения секретов — вне владения этой роли; ссылка на неё заводится
  DevSecOps-ролью, если/когда она активируется для пакета (сегодня не активирована — требование
  «Инварианты и Safeguards», `single-auth-mode.md`).

## Escalation

- On-call — оператор, инициировавший переход (пакет — локальный CLI одного владельца, не сервис с
  дежурством, тот же прецедент, что OPS-001).
- Эскалировать, если: `ktalk auth-status --json` стабильно отдаёт `alive: false` сразу после
  свежей записи токена (шаг 4 «Перехода») — признак не протухания, а неверно скопированного
  значения или проблемы на стороне контура, не решается повторным `token set`.

## Known problems

- **`echo "${VAR:-...}"` не годится для проверки «переменная задана» без утечки значения** — см.
  предупреждение в разделе «Задет ли ты»; использовать `[ -n "${VAR:-}" ]`.
- **Формулировка отказа `list-archive` после 3.0.0 не проверена дословно** — механизм (код
  возврата `1`, отказ до сети) гарантирован ADR-025, точный текст — нет; сверить при первом
  реальном прогоне на выпущенной 3.0.0 и дополнить эту таблицу.
- **`ktalk doctor` отсутствует в этом дереве** — раздел «Диагностика» ссылается на решение
  (ADR-026), не на исполненную команду; не путать одно с другим при чтении рунбука.
- **Откат данных не требуется, откат версии — да** — в отличие от OPS-001 (миграция файла реестра),
  здесь нет состояния, которое переход портит необратимо: и переход, и откат — вопрос версии пакета
  и содержимого файла токена/окружения.
