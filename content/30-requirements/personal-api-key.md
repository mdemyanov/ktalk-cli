## Контекст

Сегодня клиент авторизуется единственным способом — query-параметром `sessionToken`, токеном из
браузерной сессии, который протухает без предсказуемого срока и без диагностики: ошибка 403
неотличима от прочих сбоев. Кроме того зонд обнаружил, что `ktalk sync` в текущем виде не
работает вообще: API отклоняет `top=1000` (допустимый диапазон — 1–100), а после гипотетического
исправления только этого параметра цикл пагинации всё равно оборвался бы на первой странице —
ответ `/api/recordings` не содержит `nextPageToken`, на который опирается код. Это дефект прода,
а не техдолг.

Официальный интеграторский API (`talk.public.api-api-2.json`) открывает авторизацию персональным
ключом через заголовок `X-Auth-Token` и даёт доступ к операциям, которых у клиента сегодня нет:
скачивание файла записи, полный состав участников, архив встреч, чат, диагностика самого ключа.
Зонд показал, что набор рабочих путей жёстко зависит от режима авторизации: часть интеграторской
поверхности (`/api/Domain/*`, `/api/Recordings/*`, `/api/ConferenceReports/*`) отвечает 401/403 по
session-токену. Буквальный перенос путей «на спеку» убил бы session-режим — эпик поэтому вводит
режим по ключу как дополнение, не замену, с профилем эндпоинтов на каждый режим.

Api-key-режим получил первую живую проверку после написания этого требования (зонд PM,
2026-08-13, части 2–3). Транспорт ключа подтверждён эмпирически: заголовок `X-Auth-Token`
принимается (`200` на `/api/Users`), альтернативные схемы — `Authorization: Bearer/Session`,
`?sessionToken=`, `?apiKey=` — все дают `401`. Но выданному ключу назначен только scope
`application.profiles.read`: все эндпоинты этого эпика отвечают `403`. Нужны
`application.recording.read` (список/детали/транскрипт/саммари/полный состав участников/
скачивание) и `application.reporting.read` (архив, чат); для FR-11 через `access-info` —
дополнительно `application.applications.read`. Поведение конкретных путей под ключом с
ДОСТАТОЧНЫМИ правами по-прежнему не подтверждено ни одним запросом — экстраполяция из
[RES-001](../10-domain/research/ktalk-integrator-api.md) остаётся источником для путей и форм
ответа. Каждая такая AC явно помечена как ручная проверка на боевом домене, но её текущий статус —
не «ожидает планового прогона», а «заблокирована нехваткой прав ключа» (см. «Риски»).

## Функциональные требования

### FR-1 — Чтение ключа из переменной окружения

Клиент читает персональный API-ключ из переменной окружения `KTALK_PERSONAL_API_KEY`. Имя
переменной сознательно отличается от гипотетической `KTALK_API_KEY`: в Толке есть второй,
самостоятельный ключ пространства с заголовком `X-API-Key` — имена не должны смешиваться.

**AC:**
- Given `KTALK_PERSONAL_API_KEY` задана непустым значением, When конфигурация инициализируется,
  Then значение доступно клиенту как персональный ключ — автоматическая проверка (unit-тест
  загрузки настроек).
- Given `KTALK_PERSONAL_API_KEY` отсутствует или пуста, When конфигурация инициализируется, Then
  ошибки на этом шаге нет, ключ считается неустановленным — автоматическая проверка.

### FR-2 — Заголовок X-Auth-Token вместо sessionToken

Если ключ задан, каждый запрос к API несёт заголовок `X-Auth-Token: <ключ>`; query-параметр
`sessionToken` при этом не отправляется вовсе — не пустой, а отсутствующий.

**AC:**
- Given `KTALK_PERSONAL_API_KEY` задан, When выполняется любой запрос (список, детали,
  транскрипт, саммари и далее по FR-6..FR-11), Then запрос несёт заголовок `X-Auth-Token` и не
  несёт параметр `sessionToken` — автоматическая проверка (перехват исходящего запроса в тестах).
- Given заданы одновременно `KTALK_PERSONAL_API_KEY` и `KTALK_SESSION_TOKEN`, When клиент
  инициализируется, Then используется исключительно режим по ключу — `sessionToken` не
  запрашивается и не отправляется ни при каких обстоятельствах (см. «Инварианты и Safeguards») —
  автоматическая проверка.

### FR-3 — Обратная совместимость по умолчанию

При отсутствии `KTALK_PERSONAL_API_KEY` и наличии `KTALK_SESSION_TOKEN` клиент работает как
сегодня — `sessionToken` в query-параметрах, без заголовка `X-Auth-Token`.

**AC:**
- Given ключ отсутствует, а `KTALK_SESSION_TOKEN` задан, When выполняется запрос, Then
  используется query-параметр `sessionToken`, заголовка `X-Auth-Token` нет — автоматическая
  проверка (регрессионный тест, покрывает уже существующее поведение).
- Given ни ключ, ни session-токен не заданы, When конфигурация инициализируется, Then пользователь
  получает понятную ошибку о том, что нужна одна из двух переменных — автоматическая проверка.

### FR-4 — Базовые операции работают в обоих режимах

Список записей, детали записи, транскрипт, саммари доступны и в session-, и в api-key-режиме.
Последствие профиля эндпоинтов (FR-6): для транскрипта и саммари путь один и тот же в обоих
режимах; для списка и деталей записи режимы используют РАЗНЫЕ пути (session — внутренний контур,
api-key — официальные `Domain`-пути), результат эквивалентен по смыслу, но не гарантированно
идентичен по набору полей.

**AC:**
- Given session-режим, When вызваны список/детали/транскрипт/саммари, Then все четыре операции
  возвращают корректный результат — автоматическая проверка (уже работает сегодня, регрессия).
- Given api-key-режим, When вызваны те же четыре операции, Then все они возвращают корректный
  результат через профиль путей api-key-режима — ручная проверка на боевом домене (путь под
  ключом не проверен эмпирически на момент требования).
- Given api-key-режим, When вызван список записей за тот же период, что и в session-режиме, Then
  набор записей семантически совпадает (те же встречи), допустимые различия в служебных полях
  зафиксированы отдельно — ручная проверка (сверка).

### FR-5 — Диагностика протухшего ключа/токена и нехватки прав

Ответы 401 и 403 не долетают до пользователя голым кодом. Зонд подтвердил (Ф-12): это устойчиво
разные диагнозы, не варианты одной ошибки. 401 значит «ключ/токен невалиден или истёк», 403
значит «ключ/токен валиден, но операции не хватает прав». Тело 403 в большинстве случаев пустое —
диагностика опирается на код ответа, не на тело. Клиент различает оба случая и указывает верное
действие: на 401 — какую переменную окружения обновить, на 403 — что обновление токена/ключа НЕ
является решением проблемы.

**AC:**
- Given API вернул 401 (в любом режиме), When ошибка обрабатывается, Then пользователь видит
  русскоязычное сообщение с указанием обновить активную переменную (`KTALK_PERSONAL_API_KEY` в
  api-key-режиме, `KTALK_SESSION_TOKEN` в session-режиме) — автоматическая проверка.
- Given активен api-key-режим и API вернул 403, When ошибка обрабатывается, Then сообщение
  называет конкретный недостающий scope операции и НЕ советует обновлять ключ — автоматическая
  проверка (зонд, Ф-11/Ф-12: выданному ключу назначен только `application.profiles.read`, все
  эндпоинты эпика отвечают 403 по этой причине, не по протуханию ключа).
- Given активен session-режим и API вернул 403, When ошибка обрабатывается, Then сообщение
  говорит об отсутствии прав на операцию и явно НЕ советует обновлять токен — автоматическая
  проверка (регрессия: до этого уточнения 401 и 403 в session-режиме давали одинаковый текст
  «токен истёк», из-за чего пользователь, упёршийся в нехватку прав, шёл обновлять рабочий
  токен).
- Given формат тела ошибки не удаётся распарсить как JSON (включая пустое тело 403, зонд Ф-12),
  When ошибка обрабатывается, Then пользователь всё равно получает читаемое сообщение без сырого
  трейсбэка — автоматическая проверка.

### FR-6 — Профиль эндпоинтов по режиму авторизации

Набор используемых путей API зависит от активного режима авторизации. Формулировка «эндпоинты
привести в соответствие с `talk.public.api-api-2.json`» из постановки переформулирована: буквальный
перевод всех путей на спеку ломает session-режим (зонд, Ф-1 — интеграторская поверхность отвечает
401/403 по session-токену). Вместо этого фиксируется профиль — таблица «операция → путь по
режиму», обязательная точка опоры для SA при проектировании клиента.

| Операция | Session-режим | Api-key-режим | Проверено эмпирически |
|---|---|---|---|
| Список записей | `GET /api/recordings` (внутренний контур, вне спеки) | `GET /api/Domain/recordings/v2` (RES-001 п.2) | Session — да (200, зонд Ф-1). Api-key — нет. |
| Детали записи | `GET /api/recordings/{id}` | `GET /api/Domain/recordings/{key}` (RES-001 п.3) | Session — да. Api-key — нет. |
| Транскрипт | `GET /api/recordings/{key}/transcript` | тот же путь (RES-001 п.6) | Session — да (используется сегодня). Api-key — нет, ожидание по спеке. |
| Саммари (v2 / по типу) | `GET /api/recordings/v2/{key}/summary`, `GET /api/recordings/{key}/summary/{type}` | те же пути (RES-001 п.7–8) | Session — да. Api-key — нет. |
| Детали встречи | `GET /api/conferencesHistory/{key}` (регистронезависимо) | тот же путь (RES-001 п.11/12) | Session — да, все варианты регистра/версии (зонд Ф-1). Api-key — нет. |
| Полный состав участников | нет отдельного пути — только дообогащение (FR-8) | `GET /api/Domain/recordings/{key}/participants` (RES-001 п.4) | Api-key — нет. |
| Скачивание файла | `qualities[].fileUrl` внутри деталей записи (уже доступно) | `GET /api/Recordings/{key}/file/{qualityName}` (RES-001 п.5) | Session — поле присутствует (зонд Ф-7). Api-key — нет. |
| Архив встреч (список) | недоступен — `GET /api/domain/conferencesHistory` даёт 401 под сессией | тот же путь (RES-001 п.10) | Session — подтверждено недоступно. Api-key — нет. |
| Чат встречи | `GET /api/conferencesHistory/{key}/chat/messages?channel=…` (зонд Ф-6) | `GET /api/ConferenceReports/{key}/messages` — 401 под сессией (RES-001 п.13) | Session — да (200 с `channel=general`). Api-key — нет. |
| Отчёт по участникам встречи | аналога нет | `GET /api/ConferenceReports/{key}/participants` — 401 под сессией (RES-001 п.14) | Api-key — нет. |
| Диагностика ключа | аналога нет (сессионный токен так не диагностируется) | `GET /api/domain/applications/access-info` — 403 под сессией (RES-001, находка 8) | Api-key — нет. |

**AC:**
- Given session-режим, When клиент вызывает список/детали записи, Then используется внутренний
  контур (`/api/recordings`, `/api/recordings/{id}`), без изменений от текущего поведения —
  автоматическая проверка (регрессия).
- Given api-key-режим, When клиент вызывает список/детали записи, Then используется официальный
  путь (`/api/Domain/recordings/v2`, `/api/Domain/recordings/{key}`) — автоматическая проверка на
  уровне выбора пути (мок), боевое подтверждение — ручная проверка при появлении ключа.
- Given любая операция из группы «аналога нет» в session-режиме (участники, архив, отчёт
  участников, диагностика ключа), When она вызвана без активного ключа, Then пользователь получает
  явное сообщение «операция доступна только в режиме персонального ключа», а не голый 401/403 —
  автоматическая проверка.

### FR-7 — Скачивание видеофайла записи

Клиент отдаёт файл записи в выбранном качестве. Механизм получения ссылки различается по режиму
(см. таблицу профиля, FR-6): в session-режиме ссылка уже есть в деталях записи
(`qualities[].fileUrl`), в api-key-режиме используется отдельный путь с именем качества в шаблоне.
Зонд обнаружил конфликт именования качества: session отдаёт `900p` (без пробела), спека api-key
рекомендует `900 p` (с пробелом) — наивная сборка URL с пробелом ломается
(`InvalidURL: URL can't contain control characters`).

**AC:**
- Given session-режим и запись с доступными качествами, When запрошено скачивание, Then клиент
  берёт ссылку из `qualities[].fileUrl` деталей записи и скачивает выбранное качество — ручная
  проверка на боевом домене (сам поток скачивания зондом не проверялся, только наличие поля).
- Given api-key-режим, When запрошено скачивание, Then имя качества корректно кодируется в URL
  независимо от наличия пробела в исходном значении (`900p` и `900 p` не приводят к ошибке
  построения запроса) — автоматическая проверка (unit-тест на построение URL/квотирование).
- Given запрошено качество, которого нет в списке доступных для записи, When скачивание
  запущено, Then пользователь получает понятное сообщение с перечнем доступных качеств, а не
  необработанное исключение — автоматическая проверка.
- Given файл записи любого размера, When скачивание выполняется, Then содержимое передаётся
  потоково, а не буферизуется целиком в памяти — автоматическая проверка (контракт потоковой
  передачи).

### FR-8 — Полный состав участников встречи

Пробел «реестр показывает не всех участников» вызван не отсутствием эндпоинта, а дефолтом
`maxParticipantCount=6` у спискового эндпоинта (максимум параметра — 10, в домене есть записи с
14 участниками). Полный состав получается дообогащением по каждой записи, а не поднятием
параметра списка. Анонимные участники (`isAnonymous: true`, без `userInfo`) не должны отбрасываться.

**AC:**
- Given запись, у которой `participants[]` в списковом ответе короче `participantsCount` (зонд:
  23 из 100 записей домена), When запрошен полный состав, Then клиент дообогащает список через
  запрос по конкретной записи, а не доверяет списковому ответу — автоматическая проверка (фикстура
  записи с `participantsCount` больше длины `participants[]`).
- Given участник с `isAnonymous: true` и без `userInfo`, When состав участников формируется,
  Then анонимный участник присутствует в результате с различимым представлением (не отбрасывается
  молча) — автоматическая проверка (фикстура на основе формы `TalkUserBaseInfoRef`, RES-001).
- Given запись с числом участников больше 10 (документированный максимум параметра
  `maxParticipantCount`), When запрошен полный состав, Then все участники присутствуют в
  результате — ручная проверка на боевом домене (зонд подтвердил только случай с 8 участниками,
  случай с превышением 10 не проверен). Архитектурное решение об источнике дообогащения в
  session-режиме закрыто SA (объединение `get_recording` + `get_conference` с явным `incomplete`,
  [ADR-003](../00-project/adr/ADR-003-auth-modes.md)) — открыт только эмпирический случай >10
  участников, см. «Риски».

### FR-9 — Архив встреч (пагинация, поиск, окно дат)

Архив по режиму профиля (FR-6) доступен только в api-key-режиме — списковый путь
`/api/domain/conferencesHistory` подтверждённо недоступен под session-токеном (401, зонд).
Поддерживает пагинацию, окно по датам, поиск по комнатам.

**AC:**
- Given api-key-режим и указано окно дат, When запрошен архив, Then возвращаются встречи из
  этого окна с пагинацией в пределах документированных границ параметра количества элементов
  (1–100 по спеке, RES-001 п.10) — ручная проверка на боевом домене.
- Given окно дат содержит больше результатов, чем помещается на одну страницу, When архив
  прочитан полностью на стороне клиента, Then возвращаются все подходящие встречи, а не только
  первая страница — автоматическая проверка (тот же класс дисциплины, что и FR-14: не полагаться
  на признак пагинации, которого может не быть в ответе).
- Given session-режим (ключ не задан), When предпринята попытка получить архив, Then пользователь
  получает явное сообщение о том, что архив доступен только в api-key-режиме, а не голый 401 —
  автоматическая проверка.
- Given указан фильтр по комнатам, When архив запрошен с этим фильтром, Then результат
  ограничен указанными комнатами — ручная проверка на боевом домене.

### FR-10 — Чат встречи

Механизм получения сообщений различается по режиму (профиль, FR-6). В session-режиме зонд
подтвердил работающий путь через историю встречи с обязательным параметром канала
(`channel=general`); без канала API отвечает 400 «The channel field is required». В api-key-режиме
целевой путь — отдельный отчётный эндпоинт спеки, под сессией недоступен (401).

**AC:**
- Given session-режим и известен канал (например, `general`), When запрошены сообщения чата,
  Then они возвращаются через путь истории встречи — ручная проверка на боевом домене (зонд
  подтвердил конкретный запрос, не весь маппинг ответа).
- Given канал не указан явно, When запрошены сообщения чата, Then клиент сначала определяет
  доступные каналы (например, из списка каналов в деталях встречи), а не падает с сырым 400 —
  автоматическая проверка.
- Given api-key-режим, When запрошены сообщения чата, Then используется отчётный путь профиля
  api-key-режима — ручная проверка на боевом домене (путь не проверен эмпирически на момент
  требования).
- Given запрошен канал, к которому у ключа/токена нет доступа (API отвечает 403 с текстом «нет
  прав на получение сообщений чат-канала X»), When ошибка обрабатывается, Then пользователь видит
  понятное сообщение о нехватке прав на конкретный канал — автоматическая проверка.

### FR-11 — Диагностика токена/ключа (auth_status)

Пользователь может проверить состояние активного механизма авторизации без похода за
транскриптом или списком записей. Кандидат пути для api-key-режима —
`GET /api/domain/applications/access-info`: без параметров, отдаёт `scopes[]` и `expiredAt`,
по описанию в спеке работает и для истёкших ключей (RES-001, находка 8) — под сессией зонд
получил 403, что ожидаемо (путь входит в профиль api-key-only). Диагностика сама требует scope
`application.applications.read` — ключ без этого scope не может прочитать собственные `scopes[]`
через `access-info` (зонд, Ф-11: у выданного ключа этого scope нет); механизм деградации на этот
случай закреплён [ADR-003](../00-project/adr/ADR-003-auth-modes.md).

**AC:**
- Given api-key-режим, When вызвана диагностика, Then возвращается объём доступа ключа
  (`scopes[]`) и срок действия (`expiredAt`) живым запросом к API, а не локальным предположением —
  ручная проверка на боевом домене, заблокирована нехваткой scope `application.applications.read`
  у текущего ключа (см. «Риски»).
- Given api-key-режим и ключ истёк, When вызвана диагностика, Then результат всё равно
  возвращается (не исключение) — ручная проверка на боевом домене (спека утверждает эту
  особенность текстом, не проверена эмпирически).
- Given api-key-режим и ключу не хватает scope `application.applications.read`, When вызвана
  диагностика, Then результат не падает исключением — возвращается «ключ жив, но не может
  прочитать `scopes[]`», а не голый 403 — автоматическая проверка (регрессия ровно того случая,
  что подтвердил зонд, Ф-11).
- Given session-режим, When вызвана диагностика, Then пользователь получает честный ответ о том,
  что диагностика в этом режиме ограничена (у сессионного токена нет эндпоинта-аналога), а не
  имитацию проверки без сетевого обращения — автоматическая проверка. Механизм закрыт
  [ADR-003](../00-project/adr/ADR-003-auth-modes.md): пробный запрос `list_recordings(top=1)`,
  результат — только «токен работает / не работает», без scope и срока действия — это честный
  предел режима, а не деградация.

### FR-14 — Починка синхронизации: границы top и пагинация через skip

Зонд обнаружил, что `ktalk sync` сегодня не работает вообще: API отклоняет `top=1000` (`400
ValidationError: "The field Top must be between 1 and 100"`), а ответ `/api/recordings` не
содержит `nextPageToken` — цикл пагинации по этому полю обрывается после первой страницы. Домен
содержит ≈1316 записей. Требование новое, не входит в исходную постановку владельца.

**AC:**
- Given любой вызов синхронизации, When формируется запрос списка записей, Then значение
  количества элементов на страницу никогда не выходит за границы 1–100 — автоматическая проверка
  (регрессия дефекта top=1000).
- Given записей в выбранном окне дат больше одной страницы, When синхронизация выполняется,
  Then клиент продолжает пагинацию через `skip` до пустой страницы, не полагаясь на отсутствующее
  поле токена следующей страницы — автоматическая проверка (мок с несколькими непересекающимися
  страницами по id, проверка, что забраны все).
- Given окно дат `--days N` покрывает больше 100 записей, When `ktalk sync` завершается, Then в
  реестре оказываются все записи этого окна, а не только первые 100 — автоматическая проверка.

### FR-15 — Сверка идентификаторов перед первым api-key sync

Первичный ключ реестра сегодня берётся как `rec["id"] or rec["key"]`. Внутренний контур отдаёт
только `id`; интеграторский контур по схеме несёт и `id`, и `key` (RES-001). Совпадают ли
значения `id` между двумя контурами — не проверено (расширение прав ключа для функционального
api-key sync заблокировано, Ф-10/Ф-11). Если разойдутся, первый `ktalk sync` в api-key-режиме
задвоит реестр (≈1316 записей). Требование новое, не входит в исходную постановку владельца.

Сверка обязана сравнивать одно и то же окно дат с обеих сторон, а не окно `--days` с ВСЕМ
реестром: реестр хранит всю историю синхронизаций (на боевом домене ≈1316 строк), а из API при
`--days N` приходит только окно. Дефект был найден при реализации, до боевого прогона: при
наивном сравнении окна со всем реестром предохранитель почти всегда находил бы «пропавшие»
записи (при `--days 7` на боевом домене — ≈1218 ложных срабатываний), то есть срабатывал бы
всегда и не защищал бы ни от чего. Исправление сравнивает окно из API с той частью реестра, что
попадает в то же окно по дате.

**AC:**
- Given реестр уже содержит записи, синхронизированные в session-режиме, When впервые включается
  api-key-режим, Then перед боевым запуском синхронизации обязателен отдельный сухой прогон,
  сверяющий идентификаторы записей из api-key-ответа с записями реестра, попадающими в то же
  окно дат `--days` (не со всем реестром) — автоматическая проверка механики сравнения (функция
  сравнения двух наборов id на фикстурах, включая регрессию «окно против всего реестра») +
  обязательный ручной шаг на боевом домене перед первым боевым синком (задокументирован в README
  как обязательная процедура).
- Given сухой прогон обнаружил расхождение идентификаторов (совпадение неполное), When оператор
  видит отчёт, Then боевая синхронизация в api-key-режиме не выполняется автоматически без
  осознанного решения оператора — автоматическая проверка блокирующего поведения; фактическое
  расхождение на боевом домене — ручная проверка, заблокирована нехваткой scope
  `application.recording.read` у ключа, не отсутствием ключа как такового.
- Given сухой прогон подтвердил полное совпадение идентификаторов, When оператор подтверждает
  результат, Then обычная синхронизация в api-key-режиме может выполняться — ручная проверка на
  боевом домене, заблокирована по той же причине.

### FR-16 — Клиентское окно дат при синхронизации (`--days`)

Зонд обнаружил (Ф-15): API игнорирует параметры `startFrom`/`startTo` на `/api/recordings` —
проверено пятью вариантами запроса, выдача побитово одинакова независимо от значений фильтра.
Описания этих параметров в OpenAPI-спеке у v1 и v2 к тому же зеркальны (RES-001) — их семантике
нельзя доверять ни по имени, ни по описанию. Дефект проявился именно после починки пагинации
(FR-14): раньше цикл обрывался на первой странице, и это случайно маскировало отсутствие
серверной фильтрации. Последствие до исправления: `ktalk sync --days 30` затягивал весь домен
(1318 записей вместо ожидаемых ≈99) и в одном прогоне помечал статусом `skipped` 1220 записей.

Решение: окно `--days` обеспечивает клиент, не сервер, а обход прекращается на первой странице,
вышедшей за порог окна. Ранняя остановка безопасна только потому, что порядок выдачи проверен
зондом на пяти страницах подряд (Ф-16): строго убывающий внутри страницы и монотонный между
страницами (`orderMode=byTimeNewFirst`). Требование новое, не входит в исходную постановку
владельца.

**AC:**
- Given записей в домене больше, чем попадает в окно `--days N`, When синхронизация выполняется,
  Then клиент отбирает только записи, чья дата не старше порога окна, независимо от значений
  `startFrom`/`startTo`, фактически отправленных на сервер — автоматическая проверка (клиентское
  окно на фикстурах с датами внутри и вне порога).
- Given очередная полученная страница содержит хотя бы одну запись старше порога окна, When эта
  страница обработана, Then обход дальнейших страниц прекращается без дополнительных запросов к
  API — автоматическая проверка (мок с несколькими страницами, подсчёт фактически выполненных
  запросов).
- Given запись без разбираемой даты (пустой `createdDate`), When формируется окно, Then запись не
  отбрасывается молча — автоматическая проверка.
- Given окно `--days 7` на боевом домене (≈1316 записей), When `ktalk sync` выполнен, Then в
  реестре оказывается только окно, а не весь домен — подтверждено живым прогоном (зонд, часть 3:
  99 записей, 0 экспираций, 1,4 секунды).

## Риски

**Закрыто эмпирически зондом (session-режим, часть 1):**
- Ф-1 — какие пути доступны/недоступны по session-токену.
- Ф-2 — `top=1000` даёт 400, синхронизация сегодня не работает.
- Ф-3 — `/api/recordings` не отдаёт токен следующей страницы; `skip`-пагинация работает корректно
  (проверено на 3 страницах, пересечение — 0).
- Ф-4 — причина неполного списка участников: дефолт `maxParticipantCount=6`, 23 из 100 записей
  домена задеты.
- Ф-5 — мост `recording → conferenceKey → conferencesHistory` работает в session-режиме.
- Ф-6 — чат требует обязательный параметр `channel`; `general` — рабочее значение.
- Ф-7 — два механизма скачивания, конфликт именования качества (`900p` vs `900 p`).
- Ф-9 — формат тела ошибки API, состав полей `createdBy`, видимость статуса транскрипта до его
  запроса.

**Закрыто эмпирически зондом (api-key-режим, части 2–3):**
- Ф-10 — транспорт ключа: заголовок `X-Auth-Token` принимается (`200` на `/api/Users`);
  альтернативные схемы (`Authorization: Bearer/Session`, `?sessionToken=`, `?apiKey=`) дают `401`.
- Ф-11 — выданному ключу назначен только scope `application.profiles.read`; все эндпоинты эпика
  дают `403` без `application.recording.read`/`application.reporting.read`/
  `application.applications.read` (FR-5, FR-11).
- Ф-12 — 401 и 403 устойчиво разные диагнозы; тело 403 в большинстве случаев пустое; различение
  реализовано и покрыто тестами, в том числе для session-режима, где раньше оба кода давали
  одинаковый текст «токен истёк» (FR-5).
- Ф-15 — `/api/recordings` игнорирует `startFrom`/`startTo` (проверено пятью вариантами запроса,
  выдача побитово одинакова); описания параметров v1/v2 в спеке зеркальны (FR-16).
- Ф-16 — порядок выдачи `/api/recordings` строго убывающий внутри страницы и монотонный между
  страницами на пяти страницах подряд — ранняя остановка окна дат (FR-16) безопасна.

**ЗАБЛОКИРОВАНО нехваткой прав ключа:**
- Вся боевая проверка api-key-режима сверх транспорта и диагностики кода ответа: каждая AC этого
  документа, помеченная «ручная проверка на боевом домене» (список/детали/транскрипт/саммари,
  скачивание, полный состав участников, архив, чат, отчёт по участникам, `access-info`),
  физически не выполнима текущим ключом — API отвечает 403 без запрошенного расширения прав.
- Живая сверка идентификаторов между внутренним и интеграторским контуром (FR-15) — механизм
  реализован и покрыт тестами на фикстурах, но реальное сравнение id на боевом домене не
  проведено; риск задвоения реестра при первом боевом api-key sync остаётся НЕ закрытым.

**НЕ закрыто (открытые риски, не связаны с правами ключа):**
- Поведение эндпоинта деталей записи для записей с числом участников больше 10 — зонд проверил
  только случай с 8 участниками.
- Формат тела ошибки конкретно для 401 — нигде не объявлен в спеке (RES-001, «Что не удалось
  выяснить»); зонд подтвердил формат ошибок для 400, но не для 401, и подтвердил в основном
  пустое тело для 403 (Ф-12).
- Аномалия `qualityName: in=query` при физическом наличии в шаблоне пути — не проверено, как API
  реально ожидает параметр (RES-001).
- Совместимость lowercase-путей внутреннего контура (`/api/recordings`) с `X-Auth-Token` — эти
  пути не входят в 14 официальных эндпоинтов спеки вовсе, их поведение под ключом неизвестно.
- Пределы rate limiting (429) — нигде не задокументированы числом.

## Вне рамок

- **FR-12 — создание комнаты.** Номер зарезервирован постановкой владельца, сознательно исключён
  из этого эпика.
- **FR-13 — планирование встречи.** Аналогично, номер зарезервирован, вне рамок.
- **Файл токена + букмарклет (подход mainpart, RES-002).** Локальное хранение токена в файле,
  HTTP-приёмник на localhost, обновление через браузерный букмарклет или сторонний `chromedb` —
  не переносится. Session-режим остаётся как есть (query-параметр `sessionToken` из переменной
  окружения).
- Второй ключ пространства Толка с заголовком `X-API-Key` — не путать с персональным ключом этого
  эпика; поддержка `X-API-Key` не входит в scope.

## Инварианты и Safeguards

**Содержательные:**
- Заголовок `X-Auth-Token` и query-параметр `sessionToken` взаимно исключающие — ни один запрос
  не несёт оба одновременно (FR-2).
- Ни один запрос синхронизации не отправляет значение количества элементов на страницу вне
  диапазона 1–100 (FR-14) — закрывает класс дефекта, из-за которого `ktalk sync` не работал.
- Первичный ключ записи реестра не создаёт дублирующихся строк для уже существующей записи при
  переключении режима авторизации (FR-15) — застраховано обязательным сухим прогоном перед первым
  боевым api-key sync, сравнивающим окно `--days` из API с той же датовой границей реестра, а не
  окно со всем реестром.
- Обход синхронизации не запрашивает страницы за пределами окна `--days` (FR-16) — ранняя
  остановка опирается на подтверждённый зондом строго убывающий порядок выдачи (Ф-16).

**Sensitive content:**
- Значения `KTALK_PERSONAL_API_KEY` и `KTALK_SESSION_TOKEN` не попадают в git-историю, логи,
  трейсбэки, stdout/stderr CLI (включая `--json`), примеры в README — там только плейсхолдеры.
- Тестовые фикстуры для FR-8/FR-10 не копируют реальные ФИО и названия встреч из боевого домена
  дословно (в зонде фигурируют реальные примеры вида «Архитектурный комитет») — используются
  синтетические данные.

**Жизненный цикл:**
- Owner требования — BA/PM проекта ktalk-mcp. Первый персональный ключ получен и прогнан зондом
  2026-08-13 (BA-002): транспорт подтверждён, права ключа — только `application.profiles.read`,
  чего недостаточно для прогона функциональных ручных AC. Эта правка фиксирует результат.
  Следующая ревизия обязательна после расширения прав ключа и прогона оставшихся ручных AC на
  боевом домене — не позднее релиза 0.5.0. Точная дата следующей ревизии владельцем не
  зафиксирована — открытый вопрос.

## Открытые вопросы

- Точная процедура получения/ротации ключа в интерфейсе Толка (конкретные шаги UI) — зонд и
  RES-001 дают только текстовое описание спеки, шаги интерфейса не проверялись.
- Пределы rate limiting (429) — не задокументированы числом ни в спеке, ни зондом.
- Формат тела ошибки конкретно для кода 401 — не подтверждён (доступен пример только для 400 и
  для общего описания в `info.description`; для 403 зонд подтвердил в основном пустое тело, Ф-12).
- Кто и когда запрашивает у администратора Толка расширение прав ключа до
  `application.recording.read`, `application.reporting.read`, `application.applications.read` —
  без этого расширения ни одна ручная AC этого документа не может быть пройдена (Ф-10, Ф-11).
- Дата следующей плановой ревизии этого требования не зафиксирована владельцем.
